## Verification

`cargo xtask ci` runs this suite at Tier 1. The crate opens no device, launches
no process, and performs no privileged operation; it writes files where it is
told to and refuses everything else, so nothing here can reach a host or user
disk (SAFE-001, SAFE-002).

The interlock's tests build a real fixture tree in a temporary directory and
verify against it, rather than against a mocked manifest. A mocked filesystem
would test the interlock's arithmetic while leaving the question it exists to
answer — what happens when a real path resolves somewhere unexpected —
unasked.

## Known gaps carried into later increments

- **No Tier-2 suite exists**, so the interlock has never gated a real destructive
  operation. Every test proves it refuses; none proves what it permits, because
  nothing yet asks it for permission. That arrives with increment 2 and it is the
  most important gap in this package.
- The `a_symlink_is_refused` test is Unix-only. Windows symlink creation needs
  either Developer Mode or elevation, and SAFE-002 keeps the default suite
  unprivileged. The non-symlink path checks still run on Windows.
- Fixtures carry partition tables and on-disk signatures, not mountable file
  systems. LUKS2, LVM2, and mdraid signatures exist and are recognized by
  `libblkid`; **BitLocker, Storage Spaces, LDM, and a recognized ZFS member do
  not**, so FS-004's list is covered in part and several of ADR-C5's
  verification items still cannot be written.
- No golden-image *integration* test consumes these fixtures yet, because the
  domain types they would be parsed into are blocked at WP-010 increment 3.

## Signature fixtures: verified against a real prober

Every signature writer was checked with `libblkid` 2.41 and `wipefs` on Debian,
not against this project's reading of a format. `blkid -p -o value -s TYPE`
reports, for the generated fixtures:

| Fixture | Reported |
| --- | --- |
| `luks2-whole-disk-512.img` | `crypto_LUKS` |
| `lvm2-pv-orphan-512.img` | `LVM2_member` |
| `mdraid-1.2-member-512.img` | `linux_raid_member` |
| `ext4-with-stale-mdraid-090-512.img` | `linux_raid_member` (and `wipefs` also reports `ext4`) |

Two writers needed a checksum before any prober would accept them — LVM2's own
nibble-wise CRC and mdraid's folded word sum — and in the mdraid case `wipefs`
listed the superblock while `blkid -p` refused it, because the first enumerates
magic matches and the second validates.

**This is now automated.** Increment 1e turns the table above into
`crates/fixtures/src/prober.rs` and re-runs the tools with `cargo xtask probe`,
which CI gates as its own Linux job. The evidence:

| Evidence | Requirement or contract |
| --- | --- |
| `cargo xtask probe`, gated by the `prober-acceptance` CI job | FS-004: a fixture a real prober does not recognize proves nothing, and until now nothing re-checked that |
| `every_fixture_has_a_recorded_prober_expectation` | Exhaustive in both directions: a fixture added without a recorded expectation would silently stop being checked against any real tool |
| `the_recorded_table_matches_a_real_probe_run` | The table is compared against a verbatim capture of `libblkid` 2.41's output, so it stays tied to a measurement rather than to an opinion — and on machines with no prober |
| `the_comparison_is_capable_of_failing_in_every_direction` | A format no longer detected, a changed answer, a lost signature, and an added one are each a disagreement. A comparison that never disagrees would make `xtask probe` the fake-success path Section 12 forbids |
| `the_conflicting_and_healthy_tables_are_recorded_as_indistinguishable` | SI-35 asserted rather than observed once: if libblkid gains a way to separate ADR-C3's `Present` from `Indeterminate`, this fails and the issue narrows |
| `the_stale_signature_is_the_one_the_single_answer_interface_reports`, `the_capture_shows_both_signatures_where_only_one_is_reported` | The Part 5 asymmetry and SI-34's premise, held by a test against captured tool output rather than by a paragraph |
| `the_parsers_read_the_shapes_the_tools_actually_emit` | Parsed against verbatim output including the escaped space in an LVM version string, `wipefs`'s header row, and the empty output both tools give for blank media |
| `the_prober_check_refuses_where_its_tools_do_not_exist` | The refusal names Linux and points at the expectations, so the task reads as belonging elsewhere rather than as a broken repository |

Each fix was verified by reverting it and confirming the new tests fail — the
discipline increment 1d established and increment 1e did not apply.

**ZFS is not in the catalogue.** `libblkid` skips its ZFS prober below 64 MiB,
and at 64 MiB with the uberblock magic verified by hexdump in all four labels it
still reports nothing. The remaining condition is unestablished, and shipping a
fixture named for a format no prober recognizes would defeat the purpose of
having fixtures at all. The writer is kept and documented; the gap is here.

## Corrections from the review audit

An independent audit of `docs/reviews/PROJECT_REVIEW_2026-07-28.md` found three
signature writers whose fields were at the wrong offsets. Each was corrected and
each correction was confirmed against `libblkid`, not merely against the struct
definition.

| Defect | Symptom | Evidence of the fix |
| --- | --- | --- |
| mdraid 0.90 `set_uuid1/2/3` written at bytes 128/132/136 — words 32/33/34, which are `utime`, `state` and `active_disks` | `blkid` reported the array UUID as `fb2871eb-0000-0000-0000-000000000000`; three quarters of the identity was zero and state fields held UUID fragments | Now at bytes 52/56/60, and `blkid` reports `fb2871eb-405c-788b-e2c6-fb8cfe3b5444`. `sb_csum` is also written now, over the full 4096-byte superblock |
| LUKS2 `checksum_alg` at 24 and UUID at 32, both inside the 48-byte `label` field | The fixture had no UUID at all, on a fixture whose purpose is an encryption-layer node identity | `checksum_alg` at 72 and UUID at 168; `blkid` now reports `ID_FS_UUID=5f1c2d3e-…` where it previously reported none |

## Increment 1d: every fixture's bytes bound to its stated purpose

The review's own ranking of where this work is weakest put "tests whose names are
the safety claim" first, and named the root cause: **no test bound a catalogue
fixture's bytes to its rationale.** Every layout and signature test rebuilt its
own image from its own literals, so the catalogue was free to produce something
else entirely.

**That was measured before it was fixed.** With `luks2_whole_disk` reduced to a
blank image and `ext4_with_stale_mdraid` stripped of its mdraid half — the exact
fixture the Part 5 asymmetry finding rests on — **all 64 tests passed.** The
LUKS2 fixture would have been 4 MiB of zeros while the table above cited it for
FS-004 and LIN-003.

`crates/fixtures/src/evidence.rs` registers a claim per fixture, computed from
bytes. After the change, the same two mutations fail 29 tests and
`cargo xtask fixtures` refuses to write, naming what was lost:

```
error: could not generate fixtures: luks2-whole-disk-512.img no longer satisfies
its stated purpose (a LUKS2 header a prober will name, whole-disk, with an
identity): no LUKS magic at offset 0
```

### Two claims corrected, both of which had outrun their code

- **`corrupt_primary_header_crc` still documented itself as ADR-C3
  `Indeterminate`**, and directly contradicted `write_conflicting_backup` three
  functions below, which had already been corrected to say the opposite. The
  layout test carried the same stale claim. Both now say *recoverable*.
- **The review response's claim about `authorization_cannot_be_forged_outside_this_module`
  is false, and was corrected in the other direction.** It recorded that the test
  "reportedly stays green with `verify_target`'s body short-circuited", implying
  the interlock suite could not see that mutation. It was run: **ten tests
  fail** — every target-verification case, including traversal, subdirectory
  copies, modified bytes, and wrong names. The one named test does stay green,
  because it tests a compile-time property and not target verification, but the
  suite around it is not blind. The word "reportedly" marks a claim that was
  never executed, which is the same defect the review was written about.

### What this does not close

`catalogue::expected()` — the interlock's root of trust — builds every image with
no I/O and does **not** call `evidence::verify`. That is deliberate: it must stay
free of failure modes on the authorization path. The consequence is that evidence
gates what reaches *disk*, not what the interlock *expects*, so a catalogue whose
builder lost its purpose would still produce a self-consistent token and digest
set. The tests above fail in that case, and `generate` refuses, so the state is
unreachable through any supported path — but it is a gap in the type rather than
in the process, and increment 2 should close it when it revisits the token.
