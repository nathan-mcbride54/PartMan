## Verification

`cargo xtask ci` runs this suite at Tier 1. The crate opens no device, launches
no process, and performs no privileged operation; it writes files where it is
told to and refuses everything else, so nothing here can reach a host or user
disk (SAFE-001, SAFE-002).

The interlock's tests build a real fixture tree in a temporary directory and
verify against it, rather than against a mocked manifest. A mocked filesystem
would test the interlock's arithmetic while leaving the question it exists to
answer — what happens when a real path resolves somewhere unexpected —
unasked.

## Known gaps carried into later increments

- **No Tier-2 suite exists**, so the interlock has never gated a real destructive
  operation. Every test proves it refuses; none proves what it permits, because
  nothing yet asks it for permission. That arrives with increment 2 and it is the
  most important gap in this package.
- The `a_symlink_is_refused` test is Unix-only. Windows symlink creation needs
  either Developer Mode or elevation, and SAFE-002 keeps the default suite
  unprivileged. The non-symlink path checks still run on Windows.
- Fixtures carry partition tables and on-disk signatures, not mountable file
  systems. LUKS2, LVM2, and mdraid signatures exist and are recognized by
  `libblkid`; **BitLocker, Storage Spaces, LDM, and a recognized ZFS member do
  not**, so FS-004's list is covered in part and several of ADR-C5's
  verification items still cannot be written.
- No golden-image *integration* test consumes these fixtures yet, because the
  domain types they would be parsed into are blocked at WP-010 increment 3.

## Signature fixtures: verified against a real prober

Every signature writer was checked with `libblkid` 2.41 and `wipefs` on Debian,
not against this project's reading of a format. `blkid -p -o value -s TYPE`
reports, for the generated fixtures:

| Fixture | Reported |
| --- | --- |
| `luks2-whole-disk-512.img` | `crypto_LUKS` |
| `lvm2-pv-orphan-512.img` | `LVM2_member` |
| `mdraid-1.2-member-512.img` | `linux_raid_member` |
| `ext4-with-stale-mdraid-090-512.img` | `linux_raid_member` (and `wipefs` also reports `ext4`) |

Two writers needed a checksum before any prober would accept them — LVM2's own
nibble-wise CRC and mdraid's folded word sum — and in the mdraid case `wipefs`
listed the superblock while `blkid -p` refused it, because the first enumerates
magic matches and the second validates.

**ZFS is not in the catalogue.** `libblkid` skips its ZFS prober below 64 MiB,
and at 64 MiB with the uberblock magic verified by hexdump in all four labels it
still reports nothing. The remaining condition is unestablished, and shipping a
fixture named for a format no prober recognizes would defeat the purpose of
having fixtures at all. The writer is kept and documented; the gap is here.

## Corrections from the review audit

An independent audit of `docs/reviews/PROJECT_REVIEW_2026-07-28.md` found three
signature writers whose fields were at the wrong offsets. Each was corrected and
each correction was confirmed against `libblkid`, not merely against the struct
definition.

| Defect | Symptom | Evidence of the fix |
| --- | --- | --- |
| mdraid 0.90 `set_uuid1/2/3` written at bytes 128/132/136 — words 32/33/34, which are `utime`, `state` and `active_disks` | `blkid` reported the array UUID as `fb2871eb-0000-0000-0000-000000000000`; three quarters of the identity was zero and state fields held UUID fragments | Now at bytes 52/56/60, and `blkid` reports `fb2871eb-405c-788b-e2c6-fb8cfe3b5444`. `sb_csum` is also written now, over the full 4096-byte superblock |
| LUKS2 `checksum_alg` at 24 and UUID at 32, both inside the 48-byte `label` field | The fixture had no UUID at all, on a fixture whose purpose is an encryption-layer node identity | `checksum_alg` at 72 and UUID at 168; `blkid` now reports `ID_FS_UUID=5f1c2d3e-…` where it previously reported none |
| ext4 `s_blocks_count_lo` = 8192 blocks of 1 KiB on a 4 MiB device — a sector count used as a block count | A file system claiming twice the size of its device | Derived from the image, with `s_first_data_block` = 1 as a 1 KiB block size requires |

| Evidence | Requirement or contract |
| --- | --- |
| `the_090_set_uuid_occupies_its_four_non_adjacent_words` | FS-004 Linux RAID: the array identity is complete, not three-quarters zero |
| `the_luks2_fields_do_not_land_inside_the_label` | FS-004 LUKS and LIN-003: the encryption layer has an identity |
| `the_ext4_block_count_matches_the_device_it_is_written_to` | A fixture cannot declare a geometry its device cannot hold |
| `a_fixture_copy_in_a_subdirectory_is_refused` | SAFE-007: a target must be exactly where its fixture is generated, not merely beneath the root |

**The Part 5 asymmetry result is unaffected.** It rests on *detection behaviour* —
`wipefs` reporting both signatures while `blkid` reports one, stale one — and that
behaviour reproduces unchanged on the corrected fixture. What was wrong was the
faithfulness of the structure, not the observation drawn from it.
