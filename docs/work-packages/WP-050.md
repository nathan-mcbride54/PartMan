# WP-050: Capability engine interfaces and fixtures

- Spec version: 11.1.0
- Stage: Trustworthy read-only product (M1)
- Objective: Deliver the one capability engine every surface consults
  (CAP-005): a pure library that computes CAP-003's four-status answer —
  with its closed, versioned reason enum and remediation text — for one
  operation on one exact target, by composing the protection gate WP-010's
  domain crate already computes with runtime dependency facts, immutable
  technology limits, platform floors, and CAP-006 matrix evidence. The
  engine decides nothing the register or an ADR has not already decided:
  protection authority stays with `crates/domain`'s closure, `supported`
  is constructible only from stored qualification evidence, and a result
  is advisory UX until the helper recomputes it (CAP-007). Interfaces and
  fixtures only — no platform adapter, no planner, no RPC, no CLI or GUI
  surface, and no elevation anywhere.
- Requirement IDs: CAP-001, CAP-003, CAP-005, CAP-006, CAP-007, FS-007
  (the blocked-reason surface; the immutable-limit facts themselves are
  WP-035's inputs), MODEL-003 (schema versions on the reason enum and
  fixture format this package owns), SAFE-009 (workspace lint
  inheritance). Consumed, not claimed: CAP-002 and the protection gate
  (WP-010 increment 3g — `Operation`, `OperationClass`,
  `canonical_ranges`, `protection_gate`), CAP-004's runtime facts
  (WP-035's doctor delivers them; this engine takes them as typed
  inputs and never launches a tool itself), Section 9's floors
  (changeable only via ADR; this engine may narrow at runtime per
  CAP-004 facts and may never widen below them).
- Prerequisites: WP-000, WP-010 (through increment 3g), WP-020 (fixture
  images for integration-shaped tests)
- Test tier: T1, unprivileged. The engine is a pure library: no test
  opens a device, launches a process, reads the environment, or touches
  the network. Runtime facts arrive as constructed values in tests, the
  same way the engine receives them from callers.
- Acceptance scenarios: ACC-009's shape is held by test — a missing or
  out-of-range tool fact makes the dependent capability `blocked` with a
  remediation message — but ACC-009 itself is not claimed: it names the
  planner refusing a write step, and no planner exists until WP-060.
- Milestone sequencing, recorded so the start is honest: M0 and M0.5
  remain in progress on the README's criteria tables. Milestones gate
  integration exit, not package start (WP-035 started while M0's rows
  were partial, under the same sequential rule), and nothing in this
  package integrates a surface: the engine becomes product behavior only
  when WP-080/WP-060 and the adapters consume it, all M1-or-later
  packages themselves. Starting this package asserts no milestone exit.

CLI-001 and CLI-008 are deliberately **not** claimed: this package emits no
JSON and owns no CLI surface. The `capabilities` command's typed refusal in
`apps/cli` names this package as the engine deliverer; replacing that
refusal with real payloads is WP-080's work, consuming this engine through
its own grant. UI-* requirements stay with WP-030/WP-070's surfaces for the
same reason.

## Boundary — surfaces this package must not build

Each prohibition names its governing authority.

- **No protection computation.** The closure, verdicts, affected sets, and
  the per-pair protection gate are `crates/domain`'s (ADR-0018, WP-010
  increment 3e/3g). This engine calls `protection_gate` and maps its
  answer into CAP-003's vocabulary; re-deriving, caching-and-mutating, or
  overriding any verdict is forbidden. A `ProtectionGate::Unsupported` is
  CAP-003 `unsupported` and a `ProtectionGate::Blocked` is CAP-003
  `blocked`, always — no parameter of this engine can express permission
  the closure refused (the CAP-007 rule, held structurally).
- **No `supported` without stored evidence.** CAP-003 defines `supported`
  as apply-permitted backed by matrix evidence (CAP-006). The status is
  constructible only through a qualification-evidence value loaded from
  `docs/capabilities/`; while that store holds no qualifying row — as at
  this package's birth, when no apply path exists anywhere in the
  product — `supported` is unreachable, and that is the correct answer,
  not a gap. Nothing in this package may synthesize, default, or
  test-inject evidence into the shipped path.
- **No platform reach.** No device access, no subprocess, no platform
  API, no elevation. Runtime facts (tool presence, versions, mount
  state, boot role, OS identity) are typed inputs supplied by callers;
  producing them is WP-035's doctor today and the platform adapters'
  work (WP-W100/WP-L100/WP-M100) tomorrow. The engine narrowing on those
  facts may never widen below Section 9's floors.
- **No planner, no plan authority.** Capability answers condition
  planning; they never construct steps. `PlanStep::mutating` and the
  plan boundary stay WP-010's; the planner consuming both is WP-060's.
- **No client-visible surface.** No JSON schema, no CLI wiring, no GUI
  binding. CAP-005 is satisfied by every surface calling this one
  library, each under its own package's grant.
- **No multipath sameness inference.** The multipath reason in the
  closed enum reports ADR-0011's detection-only rule (`unsupported` with
  the multipath reason, per LIN-006); the engine never infers cross-path
  device identity (the standing decision, spec 4.3.0).

## Increments

1. **The vocabulary crate.** `crates/capability` workspace member
   (`[lints] workspace = true`, `unsafe_code` denied by inheritance,
   `//!` docs), depending on `partman-domain` deliberately — this crate
   exists to compose the domain's gate, and the dependency is the point,
   stated here so nobody mistakes the CLI chassis's empty-closure guard
   for a workspace-wide rule. CAP-003's status vocabulary as types:
   `supported`/`preview`/`unsupported`/`blocked` with `supported`
   constructible only through the CAP-006 evidence token (a private-field
   type with no public constructor in this increment, so the compiler
   holds the boundary until increment 3 defines the store), the closed
   reason enum — MODEL-003-versioned, the home for gated-state reporting
   the register's round-three record fixes, carrying at birth the reasons
   decided texts already name: the protection grounds mapped from
   `RefusalGround`/`IndeterminateGround`, the multipath detection-only
   reason (ADR-0011, LIN-006), missing-tool and version-out-of-range
   (ACC-009), technology-limit (FS-007), platform-floor (Section 9),
   and unqualified-pending-evidence (CAP-003's `preview` ground) — and
   remediation as structured text carried beside the reason, never
   synthesized from it. Converts the traceability mode to `generated`.
2. **The engine core.** CAP-001's conditioning: one entry point
   computing the status for (operation, target) over a decoded
   `TopologySnapshot`, its authenticated facts, and a typed
   runtime-facts input (tool availability and versions in CAP-004's
   shape, mount state, boot role, OS identity, floors) — composing, in
   refusal-precedence order, the domain's `protection_gate`, technology
   limits (FS-007), platform floors (Section 9), and runtime
   preconditions (ACC-009's `blocked`). Source-class operations are
   never suppressed by protection (3g's rule, preserved through the
   composition). CAP-005 agreement with the plan constructor is held by
   test over every operation/target pair of a fixture topology: what the
   engine calls constructible, `PlanStep::mutating` constructs, and what
   it refuses, the constructor refuses on the same ground.
3. **The CAP-006 store.** The `docs/capabilities/` format: a versioned,
   schema-checked fixture layout for qualification evidence per
   platform/file-system/operation combination, plus the per-tool version
   floors Section 9 points here. The store ships structured and empty of
   qualifications: every advertised combination's row exists with its
   unqualified state explicit, so absence is a value and `supported`
   stays unreachable until a real qualification lands under its own
   review. The evidence-token type gains its one constructor: loading a
   qualifying row from this store.
4. **The consumer seams.** The engine's public API documented for its
   three consumer classes (CLI via WP-080, planner via WP-060, adapters
   via WP-W100/L100/M100), integration-shaped tests over WP-020 fixture
   topologies exercising every CAP-003 status and every reason at least
   once, and the package record sweep: README row, CHANGELOG, and the
   generated traceability current.

## Verification

Every increment: `cargo xtask ci`, `cargo xtask test --tier 1`,
`cargo xtask verify-change-ownership --base origin/main`, real exit codes
checked. Increment 1 adds the crate to the workspace gates and converts
traceability; increment 2 adds the CAP-005 agreement enumeration;
increment 3 adds the store's schema check to CI so a malformed or
silently-qualified row fails the gate; increment 4 adds the
all-statuses/all-reasons coverage test. No requirement is recorded as
delivered without a generated traceability row backed by a live test.
