- Spec version: 4.0.0
- Objective: Establish PartMan's visual language as data, and an automated
  harness that computes the accessibility properties the specification requires
  of it rather than recording that someone once checked.

- Prerequisites: WP-000
- Test tier: T1, unprivileged
- Acceptance scenarios: none directly assigned. ACC-011 (keyboard-only
  accessible apply) depends on this package but cannot be exercised until a
  shell and a plan flow exist.

### Decision: the path is `apps/desktop/`, not `apps/shell/`

Decided 2026-07-29 by the decision owner, recorded because the second follow-up
audit rightly said the deviation should be decided rather than inherited. The
first reservation said `apps/shell/**`, which was a deviation from §4.3 nobody
had chosen.

Section 4.3's proposed layout is `apps/desktop/` beside `apps/cli/`, and §4.1
separately calls the component "Desktop shell: Tauri 2" — so *shell* is the
specification's own word for the thing, just not for the path. Following §4.3
costs nothing and settles two problems the deviation would have created:

- **`apps/cli/` is coming, and it is a different work package.** Section 14
  assigns the CLI to WP-080, and CLI-001…008 are normative. Two front ends
  named on one axis — `desktop` and `cli`, by how a user reaches them — stay
  parallel forever. `shell` beside `cli` mixes a role name with a form-factor
  name and invites the fair question of whether the CLI is a shell too.
- **"Shell" is overloaded in exactly this product.** SAFE-004 already governs
  how PartMan invokes external tools, and the product ships a real command-line
  interface. A directory called `shell` that is emphatically *not* the
  command-line thing is a misreading waiting to happen.

"Desktop shell" remains the component's name in prose, matching §4.1. The
directory follows §4.3. Nothing is deviating.

`packages/ui/**` was **missing** from the first reservation and is also §4.3's.
Without it the first shell pull request would have edited an unclaimed path and
failed `cargo xtask verify-ownership` — the reservation existed precisely to
stop that, and it had the gap it was written to prevent.

`apps/desktop/` is the Tauri application: the Rust `src-tauri` crate plus the
React and TypeScript front end. `packages/ui/` holds shared components and
`packages/design-tokens/` the generated typed accessor the audits asked for — the
front end must **not** copy the palette, so that package emits typed styles from
`schemas/design-tokens.json` and the desktop shell consumes only those.

### Still to decide before increment 2 opens

The audit is right that reserved paths alone do not make the shell
dependency-ready. These are open questions, not decisions:

- **Root Cargo integration.** `apps/desktop/src-tauri` is a workspace member, so
  adding it edits root `Cargo.toml` and `Cargo.lock`, both WP-000's. That is the
  unavoidable ownership crossing, and it needs its own reviewed WP-000 change
  rather than an edit carried along with feature work.
- **Package manager and Node policy**, and whether its configuration is
  app-local under `apps/desktop/` or root-level. Root-level files would need
  their own assignment; app-local keeps them inside this reservation.
- **Whether the shell gets its own required CI job.** If job names or matrix
  entries change, branch protection's required-check list must change in the
  same coordinated commit — a renamed job leaves every pull request waiting
  forever on a check that will never report.
- **A check that the front end uses no colour pairing policy has not
  declared**, which the audits asked for and which the current harness cannot
  see, since it only reads the token file.

## What increment 1 delivers

`schemas/design-tokens.json` is the single source of truth. It lives in
`schemas/` for the same reason `canonical-encoding-vectors.json` does: when the
Tauri front end arrives it must read *this* file. `AGENTS.md` already records
the lesson for the canonical codec — an implementation checked against a table
it also owns proves only self-consistency — and a second copy of the palette
would reintroduce exactly that.

`crates/tokens` reads it and computes three things:

| Requirement | What is computed |
| --- | --- |
| UI-001 | A dark charcoal default, an accessible high-contrast theme, and a light system theme all exist, and **all three define the same set of roles**. A role present in `dark` and missing from `high-contrast` is a component that renders in the default theme and falls back to nothing in the theme whose entire purpose is legibility. |
| UI-003 | The entity, severity and progress vocabulary matches the specification exactly, in both directions. A required role cannot be deleted and a new meaningful role cannot be invented without editing `policy.rs` and naming the requirement it serves. |
| UI-007 | Every role that carries identity, risk, or state declares an icon, a label, and a shape, so colour is never the only carrier. No two roles share an icon *and* a label, which is the one way the table can be filled in completely and still fail to do its job. |
| UI-008 | Every declared foreground/background pairing meets its WCAG 2.2 AA threshold — 4.5:1 for text (SC 1.4.3), 3:1 for user-interface components (SC 1.4.11) — in every theme. |

**The policy lives outside the file it judges.** `crates/tokens/src/policy.rs`
holds the WCAG floors, the colour-separation floor, the required themes, and the
required role vocabulary. `schemas/design-tokens.json` restates the floors so a
front end can read them, and the audit requires the restatement to *agree* — a
lowered value is a finding, not a new setting. This arrangement is a correction;
see "What the audit found" below for what it replaced and why.

Plus a colour-vision **smell test**: role pairs whose confusion would mislead a
user about risk are simulated under protanopia, deuteranopia and tritanopia and
required to stay apart by a CIE76 floor.

Run it with `cargo xtask tokens`. It is part of `cargo xtask ci`.

## The finding this package was worth doing for

The first palette written for this increment — chosen by eye, and looking
perfectly reasonable — failed its own harness on ten counts. The one that
matters:

```
severity.reversible against severity.destructive under deuteranopia
  is delta-E 10.1, below the 12 floor
```

`Reversible` is PLAN-004 severity 1, "fully undoable via an emitted reversal
plan". `Destructive` is severity 4, "data is intentionally destroyed". They were
mint green and salmon red — obviously different to a colour-sighted reviewer,
and nearly the same colour to a red-green colour-blind one. In the
high-contrast theme, the theme a low-vision user is most likely to select, the
same pair measured **delta-E 4.8**.

Three more pairs failed the same way, and three border colours sat under
WCAG's 3:1 floor for interface components.

The fix was not to lower the floor. The severity ramp now varies in **lightness
as well as hue**, because lightness survives every colour-vision deficiency
while the red-green axis does not, and the light theme uses a teal-leaning green
for `reversible` so it retains a blue component that deuteranopia preserves.
The closest surviving pair is delta-E 21.9 against a floor of 12.

## What the audit found

`docs/reviews/PROJECT_AUDIT_2026-07-29.md` demonstrated two fail-open paths in
increment 1. Both were reproduced before being fixed, and both are worth
recording because they are the same mistake in two places.

**The audited file supplied the standard it was audited against.** The contrast
floors were read from `contrastRules.thresholds` — in the file under audit.
Lowering the `text` floor to 3.0 and dimming `text.secondary` to match let
normal-size text pass the complete Tier-1 gate at **3.33:1**, well under
SC 1.4.3's 4.5:1. The colour-separation floor had the same shape.

This is precisely the failure `AGENTS.md` records for the canonical vectors —
"an implementation checked against a table it also owns proves only
self-consistency" — committed inside the harness written to enforce that rule on
colours. Increment 1's mutation table mutated *colours* thoroughly and never
mutated the *policy*, so it could not see it.

**The palette owned its own vocabulary.** The required roles were discovered by
reading the dark theme's keys and filtering for three prefixes. Deleting
`entity.container` from all three themes, the pairing list, and the channel
table left the gate green — 228 checks instead of 234 — even though UI-003
requires containers to be distinguished. A coordinated omission was
indistinguishable from a smaller product.

Both are fixed in increment 1a. `crates/tokens/src/policy.rs` holds the floors
and the vocabulary; the audit's own reproductions now produce 3 and 2 findings
respectively. Eleven mutations were added covering threshold lowering, threshold
removal, role deletion, pairing removal, risk-pair removal, role invention, and
a mismatched specification version. Deleting either new check fails the table by
name.

The reader is also genuinely strict now: `deny_unknown_fields` throughout, with
prose modelled as explicit `note` fields. Previously a misspelled
`nonColorChannels` key would have silently disabled the whole UI-007 check while
leaving a file that looked complete.

## What this does not establish

Recorded here rather than left to be assumed, because "the accessibility harness
runs" is exactly the sentence a reader will over-extend:

- **It renders nothing.** UI-008 also requires keyboard-only operation, correct
  screen-reader semantics, 200% zoom, and reduced motion. None of those can be
  satisfied by a token file and none are inspected. They belong to increments 2
  and 3.
- **Only declared pairings are checked.** A surface the front end invents, or a
  pairing it makes that is not in the file, is not covered. This is the harness's
  sharpest limitation, and it becomes load-bearing the moment a shell exists —
  increment 2 must add a check that the front end uses no colour combination
  absent from `contrastRules.pairings`.
- **The colour-vision check is a model, not a proof.** Machado (2009) simulation
  and CIE76 difference, the crudest of the delta-E formulae. Passing is not
  evidence that two colours are distinguishable in practice. **UI-007's
  redundant channels are the guarantee**; the simulation exists to catch two
  roles collapsing onto one another, which is a design mistake worth failing a
  build over.
- **The non-colour channels are declared, not rendered.** The file says
  `severity.destructive` carries a `triangle-exclamation` icon and the label
  "Destructive". Nothing yet checks that a component actually draws them. That
  check requires a shell and belongs with it.

## Evidence discipline

Every check is paired with a mutation it must reject, in
`crates/tokens/src/audit/tests.rs`. Each row was confirmed by deleting the check
it targets and observing the table go red — a deletion sweep, run because WP-020
found a gate in `generate` that was load-bearing on nothing and kept 74 tests
green when removed.

| Check deleted | Mutation table |
| --- | --- |
| `check_color_vision` | FAILED — "'reversible' and 'destructive' become the same colour" was accepted |
| duplicate icon/label detection | FAILED — "two roles share an icon and a label" was accepted |
| unknown-role detection | FAILED — "channels are declared for a role that does not exist" was accepted |

The colour maths is anchored outside this repository: black on white is WCAG's
published 21:1, a colour against itself is 1:1, and black against white is
delta-E 100 because CIELAB lightness runs 0..=100 by construction. The
colour-vision matrices are checked by their *defining qualitative property* —
red and green converge under protanopia and deuteranopia but not under
tritanopia, and greys are left untouched by all three — rather than by trusting
their digits, so a mistyped coefficient surfaces as a pair that failed to
converge instead of a plausible number with nothing to check it against.
