# WP-030: Design tokens, dark UI shell, accessibility harness

- Spec version: 4.1.0
- Objective: Establish PartMan's visual language as data and an automated
  accessibility harness; preserve the immutable Tauri 2 comparison baseline;
  and conduct ADR-0009's bounded, off-main Slint 1.17.1 production-feasibility
  evaluation for the same read-only four-region shell. Tauri 2, React, and
  TypeScript remain the normative production stack under specification 4.1.0.
  Every candidate uses synthetic data and performs no storage discovery,
  planning, execution, helper contact, or elevation.
- Requirement IDs: SAFE-001, SAFE-002, SAFE-004, SAFE-009, MODEL-001, UI-001,
  UI-002, UI-003, UI-007, UI-008, UI-011, UI-013, PLAN-004, SEC-005, SEC-007,
  SEC-010, PKG-001, PKG-002, PKG-003, PKG-004, PKG-005, Section 4.1,
  Section 9, Section 11.7, Section 12
- Prerequisites: WP-000, ADR-0009
- Test tier: T1, unprivileged
- Acceptance scenarios: none directly assigned. ACC-011 (keyboard-only
  accessible apply) depends on this package. Increment 2 is scoped to supply the
  synthetic shell and feasibility evidence only; the scenario remains blocked
  on real plan, apply, authorization, and progress flows plus complete keyboard
  and assistive-technology evidence. No ADR-0009 probe enables T2 or T3.

Increment 2 was reviewed against the active 4.1.0 specification. The canonical
design-token file remains pinned to its 4.0.0 vocabulary because 4.1.0 added
MODEL-006 and ADR-C6 without changing this package's UI or safety contract; a
token-version bump with no token-contract change would manufacture evidence
rather than improve it.

### Decision: the path is `apps/desktop/`, not `apps/shell/`

Decided 2026-07-29 by the decision owner, recorded because the second follow-up
audit rightly said the deviation should be decided rather than inherited. The
first reservation said `apps/shell/**`, which was a deviation from §4.3 nobody
had chosen.

Section 4.3's proposed layout is `apps/desktop/` beside `apps/cli/`, and §4.1
separately calls the component "Desktop shell: Tauri 2" — so *shell* is the
specification's own word for the thing, just not for the path. Following §4.3
costs nothing and settles two problems the deviation would have created:

- **`apps/cli/` is coming, and it is a different work package.** Section 14
  assigns the CLI to WP-080, and CLI-001…008 are normative. Two front ends
  named on one axis — `desktop` and `cli`, by how a user reaches them — stay
  parallel forever. `shell` beside `cli` mixes a role name with a form-factor
  name and invites the fair question of whether the CLI is a shell too.
- **"Shell" is overloaded in exactly this product.** SAFE-004 already governs
  how PartMan invokes external tools, and the product ships a real command-line
  interface. A directory called `shell` that is emphatically *not* the
  command-line thing is a misreading waiting to happen.

"Desktop shell" remains the component's name in prose, matching §4.1. The
directory follows §4.3. Nothing is deviating.

`packages/ui/**` was **missing** from the first reservation and is also §4.3's.
Without it the first shell pull request would have edited an unclaimed path and
failed `cargo xtask verify-ownership` — the reservation existed precisely to
stop that, and it had the gap it was written to prevent.

On the preserved Tauri comparison branch, `apps/desktop/` is the Tauri
application: the Rust `src-tauri` crate plus the React and TypeScript front end.
`packages/ui/` holds shared components and `packages/design-tokens/` the
generated typed accessor the audits asked for—the front end must **not** copy
the palette, so that package emits typed styles from
`schemas/design-tokens.json` and the desktop shell consumes only those. On the
Slint feasibility branch, `apps/desktop/` is instead the single native Rust
candidate described above; neither Tauri's web packages nor `src-tauri` exist
on that branch. No branch may contain both implementations.

### Integration decisions for increment 2

Decided 2026-07-30, because the audit was right that reserved paths alone do not
make the shell dependency-ready. Each is decided from evidence already in the
repository rather than from preference, and each says what would reopen it.

**1. Package manager: npm.** Not a preference — `packages/canonical` already
uses it, and `docs/quality/dependency-policy.md` builds a policy on that:
`package-lock.json` committed, `npm ci` in CI so a different tree fails rather
than resolving silently, `devDependencies` pinned to exact versions, and
`npm audit --audit-level=moderate` gating. A second package manager would mean a
second lockfile format, a second audit story, and a second Dependabot ecosystem
for one product. Reopen only if Tauri tooling requires something npm cannot do.

**2. Node configuration is app-local**, under `apps/desktop/`. Root-level files
would need their own WP-000 assignment and would couple the shell's tooling to
the repository root for no gain. The Node version stays pinned the way the
existing job pins it — exactly, in the workflow, with `engines` in
`package.json` as the human-readable floor.

**3. Root Cargo integration lands *with* the shell, not before it.**
*Corrected 2026-07-30. This decision originally said a WP-000 pull request would
add the workspace member and the lockfile entry first, and WP-030 would then
build the shell. That sequence cannot be executed. It was written from the shape
of the ownership rules rather than from an attempt, and attempting it is what
found the problem.*

Three measurements against `02ec952`:

- A minimal `apps/desktop/src-tauri` plus its member line, committed as
  `Work-Package: WP-030`, is **refused** for `Cargo.lock` and `Cargo.toml`.
- The identical tree committed as `Work-Package: WP-000` is **refused** for
  `apps/desktop/src-tauri/Cargo.toml` and its `src/main.rs`, because
  `apps/desktop/**` is this package's reservation. Neither package could take
  the first step.
- The member line cannot land alone either. Cargo refuses to load a workspace
  whose member has no manifest — `failed to read
  apps\desktop\src-tauri\Cargo.toml` — and a glob does not rescue it:
  `apps/*/src-tauri` matching nothing falls back to the literal path and fails
  identically. `cargo xtask ci` would have been red for everyone in between.

The deadlock is not this package's. `Cargo.lock` is WP-000's alone, so WP-010
adding a dependency to `crates/domain` hits the same wall; nobody had noticed
because no dependency-changing change had been attempted since the gate landed.

Three changes fix it, and all must land before increment 2:

1. **WP-000** teaches `verify-change-ownership` that a lockfile is *generated*.
   A `derived-paths` declaration lets any package carry `Cargo.lock` alongside a
   manifest that lockfile resolves; a lockfile moving on its own stays refused.
2. **Governance** shares root `Cargo.toml` with this package only for the
   branch-specific member set enumerated above: `apps/desktop/src-tauri` on the
   Tauri control, or `apps/desktop` and `tools/slint-feasibility` on the Slint
   candidate. This is a sub-file grant, so it remains a review obligation the
   checker cannot see, exactly like `tools/xtask/**` and this package's status
   rows in `README.md`.

3. **WP-000** also makes the inventory and the change gate agree about a
   reservation. *Added after this decision was first written, because an
   adversarial pass proved the sentence below false as originally stated: the
   scaffold commit passed `verify-change-ownership` and then failed `cargo xtask
   ci`, because `verify_path_ownership` did not count a matching
   `owned-paths-reserved` claim as coverage and reported `apps/desktop/**` as
   "claimed by no work package". No promotion route out was both green and legal.
   A reservation counts once it matches something.*

On the preserved increment-2T comparison branch, the crate, member line and
lockfile churn were added as one coherent change, and `cargo xtask ci` remained
green at every commit. That historical claim was checked by building the
scaffold against the composed branches rather than asserted — see the
increment-2T checklist below for the things the gate refuses that a generated
Tauri project would otherwise trip over. PR #85 remains off-main comparison
evidence; this paragraph does not authorize landing it.

### Increment 2T checklist, measured rather than guessed

Each of these was hit by actually scaffolding the crate against the composed
state. They are cheap to fix and expensive to discover one at a time:

- **`src/main.rs` must open with a `//!` crate doc.** `missing_docs = "warn"` in
  `[workspace.lints.rust]` plus `-D warnings` in the CI clippy line makes it an
  error, unconditionally. A Tauri template's generated `main.rs` does not satisfy
  it.
- **The crate manifest must carry `[lints] workspace = true`.** Without it a
  member silently escapes `unsafe_code = "deny"`, `missing_docs` and clippy
  pedantic — which matters most for exactly this crate, the one most likely to
  want FFI. `cargo xtask ci` now rejects every workspace member that omits this
  inheritance, so the former review-only gap is closed.
- **Any `package.json` needs a root-level `"license": "MIT OR Apache-2.0"`**, or
  `verify-licenses` refuses it. A generated Tauri or Vite manifest has no licence
  field.
- **The npm half of the supply-chain gate used to be hardcoded to
  `packages/canonical`.** WP-000 closed that gap before increment 2: it now
  discovers every `package.json`, refuses one without a committed lockfile, and
  audits every discovered package. The shell still needs its own exact
  Dependabot directory entry; this assignment authorizes only that entry.

**The Tauri dependency tree was reviewed as a second, separate question.** PR
#85 resolved and tested that graph under `deny.toml` and
`docs/quality/dependency-policy.md`; the baseline/advisory decision preserves
the result off-main for comparison rather than admitting it to the product. The
derived rule permits lockfile churn, but never decides by itself whether a new
dependency graph should enter this repository's supply chain.

**4. No new required CI job.** The shell's typecheck, lint and build are steps
in the existing Tier-1 job, because a new job means a new required-status-check
name, and adding one without updating branch protection in the same change
leaves every pull request waiting forever on a check that never reports. The
Slint candidate follows the same rule. The former
`.github/workflows/desktop.yml` reservation is removed by this governance
change; a later dedicated workflow needs its own assignment and must update the
required-check list in the same change.

*Corrected 2026-07-31.* The decision above originally named the existing
Tier-1 job without granting WP-030 any part of its workflow, and it did not
authorize adding the shell to Dependabot. That made the implementation
"dependency-ready" only on paper: it could create the application but could not
make its checks mandatory or its pins maintainable. The two exact sub-file
grants above close that governance gap without transferring ownership of CI or

The first correction still omitted one prerequisite that only became concrete
when the dependency tree was inspected: Tauri's `wry` runtime enables

include the development package. Tauri's own prerequisite list requires

**5. Increment 2T/Tauri-only: the front end may not contain a colour literal.**
The audits asked for a check that the shell uses no pairing the policy has not
declared, and the token harness cannot see it because it only reads the token
file. The enforceable form of that rule:

- `packages/design-tokens/` generates typed accessors from
  `schemas/design-tokens.json`. Generated output, never hand-edited, and a dirty
  regeneration fails CI — the same shape Section 11.7 wants for traceability.
- `apps/desktop/` and `packages/ui/` may reference colour **only** through those
  accessors. A check greps them for hex literals, `rgb(`/`hsl(`/`oklch(` and
  named CSS colours, and fails on any hit.

*Revised 2026-07-30, because the grep was to be the sole enforcement boundary and
this repository has now had a lexical boundary defeated four times — three in the
action scanner, once in the lockfile rule that was written the day before. A
deny-list over CSS and TypeScript would have to understand comments, test
fixtures, SVG attributes, CSS escapes, template strings, generated output and
whatever colour syntax CSS gains next. It will age exactly as the others did.*

The grep stays, but as the outermost and weakest layer, not the boundary:

1. **Generate** CSS custom properties and TypeScript role types from
   `schemas/design-tokens.json`; a dirty regeneration fails CI.
2. **Make the type the boundary.** Components consume a small typed style API
   keyed by role, not arbitrary colour strings — so the common case is enforced
   by the compiler rather than by a search for what the compiler allowed.
3. **Validate the pair where it is declared.** A component or story states its
   foreground/background *roles*; that tuple is checked against
   `contrastRules.pairings` at definition time. This is the check the audits
   actually asked for, and it catches an undeclared pairing before any renderer
   exists.
4. **Grep as defence in depth**, with an explicit allow-list for generated files.
5. **Increment 3 inspects computed styles** in rendered states, to prove the
   declared pair is the one a user sees.

Layers 1–3 are increment 2T. Increment 2S does not inherit this CSS/TypeScript
contract: it uses ADR-0009 G-CFG-05's generated typed `.slint` interface,
generated wrappers, and AST/lowered-IR enforcement boundary. What none of
these static layers establishes, and what must not be claimed before increment
3 exists: that the colour finally painted is the colour declared. A grep cannot
see a colour computed at runtime, and a role tuple checked at definition time is
a promise about intent, not evidence about pixels.

## What increment 1 delivers

`schemas/design-tokens.json` is the single source of truth. It lives in
`schemas/` for the same reason `canonical-encoding-vectors.json` does: when the
Tauri front end arrives it must read *this* file. `AGENTS.md` already records
the lesson for the canonical codec — an implementation checked against a table
it also owns proves only self-consistency — and a second copy of the palette
would reintroduce exactly that.

`crates/tokens` reads it and computes three things:

| Requirement | What is computed |
| --- | --- |
| UI-001 | A dark charcoal default, an accessible high-contrast theme, and a light system theme all exist, and **all three define the same set of roles**. A role present in `dark` and missing from `high-contrast` is a component that renders in the default theme and falls back to nothing in the theme whose entire purpose is legibility. |
| UI-003 | The eight storage-entity roles match UI-003 exactly, in both directions. A required entity cannot be deleted and a new entity role cannot be invented without editing `policy.rs`. This is static vocabulary evidence, not evidence that a shell distinguishes the entities visually and textually. |
| PLAN-004 | The five ordinal risk-severity roles match PLAN-004 exactly and findings for missing or invented severity roles name PLAN-004. |
| UI-011 | The eight progress-state roles match UI-011 exactly and findings for missing or invented progress roles name UI-011. This does not establish a rendered progress surface or live state transitions. |
| UI-007 | Every role that carries identity, risk, or state declares an icon, a label, and a shape, so colour is never the only carrier. No two roles share an icon *and* a label, which is the one way the table can be filled in completely and still fail to do its job. |
| UI-008 | Every declared foreground/background pairing meets its WCAG 2.2 AA threshold — 4.5:1 for text (SC 1.4.3), 3:1 for user-interface components (SC 1.4.11) — in every theme. |

**The policy lives outside the file it judges.** `crates/tokens/src/policy.rs`
holds the WCAG floors, the colour-separation floor, the required themes, and the
required role vocabulary. `schemas/design-tokens.json` restates the floors so a
front end can read them, and the audit requires the restatement to *agree* — a
lowered value is a finding, not a new setting. This arrangement is a correction;
see "What the audit found" below for what it replaced and why.

Plus a colour-vision **smell test**: role pairs whose confusion would mislead a
user about risk are simulated under protanopia, deuteranopia and tritanopia and
required to stay apart by a CIE76 floor.

Run it with `cargo xtask tokens`. It is part of `cargo xtask ci`.

## The finding this package was worth doing for

The first palette written for this increment — chosen by eye, and looking
perfectly reasonable — failed its own harness on ten counts. The one that
matters:

```
severity.reversible against severity.destructive under deuteranopia
  is delta-E 10.1, below the 12 floor
```

`Reversible` is PLAN-004 severity 1, "fully undoable via an emitted reversal
plan". `Destructive` is severity 4, "data is intentionally destroyed". They were
mint green and salmon red — obviously different to a colour-sighted reviewer,
and nearly the same colour to a red-green colour-blind one. In the
high-contrast theme, the theme a low-vision user is most likely to select, the
same pair measured **delta-E 4.8**.

Three more pairs failed the same way, and three border colours sat under
WCAG's 3:1 floor for interface components.

The fix was not to lower the floor. The severity ramp now varies in **lightness
as well as hue**, because lightness survives every colour-vision deficiency
while the red-green axis does not, and the light theme uses a teal-leaning green
for `reversible` so it retains a blue component that deuteranopia preserves.
The current audit's tightest contrast is **3.57:1** for `border.default` on
`surface.base` in the light theme, against the 3.0 user-interface floor. Its
closest surviving colour-vision pair is delta-E 21.9 against a floor of 12.

## What the audit found

`docs/reviews/PROJECT_AUDIT_2026-07-29.md` demonstrated two fail-open paths in
increment 1. Both were reproduced before being fixed, and both are worth
recording because they are the same mistake in two places.

**The audited file supplied the standard it was audited against.** The contrast
floors were read from `contrastRules.thresholds` — in the file under audit.
Lowering the `text` floor to 3.0 and dimming `text.secondary` to match let
normal-size text pass the complete Tier-1 gate at **3.33:1**, well under
SC 1.4.3's 4.5:1. The colour-separation floor had the same shape.

This is precisely the failure `AGENTS.md` records for the canonical vectors —
"an implementation checked against a table it also owns proves only
self-consistency" — committed inside the harness written to enforce that rule on
colours. Increment 1's mutation table mutated *colours* thoroughly and never
mutated the *policy*, so it could not see it.

**The palette owned its own vocabulary.** The required roles were discovered by
reading the dark theme's keys and filtering for three prefixes. Deleting
`entity.container` from all three themes, the pairing list, and the channel
table left the gate green — 228 checks instead of 234 — even though UI-003
requires containers to be distinguished. A coordinated omission was
indistinguishable from a smaller product.

Both are fixed in increment 1a. `crates/tokens/src/policy.rs` holds the floors
and the vocabulary; the audit's own reproductions now produce 3 and 2 findings
respectively. Eleven mutations were added covering threshold lowering, threshold
removal, role deletion, pairing removal, risk-pair removal, role invention, and
a mismatched specification version. Deleting either new check fails the table by
name.

The reader is also genuinely strict now: `deny_unknown_fields` throughout, with
prose modelled as explicit `note` fields. Previously a misspelled
`nonColorChannels` key would have silently disabled the whole UI-007 check while
leaving a file that looked complete.

## What this does not establish

Recorded here rather than left to be assumed, because "the accessibility harness
runs" is exactly the sentence a reader will over-extend:

- **It renders nothing.** UI-008 also requires keyboard-only operation, correct
  screen-reader semantics, 200% zoom, and reduced motion. None of those can be
  satisfied by a token file and none are inspected. They belong to increments 2
  and 3.
- **Static vocabulary is not rendered distinction or live progress.** The
  harness proves that UI-003's eight entity-role names and UI-011's eight
  progress-state names exist. It does not prove that a shell distinguishes
  entities visually and textually, renders a persistent progress surface, or
  moves through the UI-011 states correctly. Those claims require increments 2
  and 3.
- **Only declared pairings are checked.** A surface the front end invents, or a
  pairing it makes that is not in the file, is not covered. This is the harness's
  sharpest limitation, and it becomes load-bearing the moment a shell exists —
  increment 2 must add a check that the front end uses no colour combination
  absent from `contrastRules.pairings`.
- **The colour-vision check is a model, not a proof.** Machado (2009) simulation
  and CIE76 difference, the crudest of the delta-E formulae. Passing is not
  evidence that two colours are distinguishable in practice. **UI-007's
  redundant channels are the guarantee**; the simulation exists to catch two
  roles collapsing onto one another, which is a design mistake worth failing a
  build over.
- **The non-colour channels are declared, not rendered.** The file says
  `severity.destructive` carries a `triangle-exclamation` icon and the label
  "Destructive". Nothing yet checks that a component actually draws them. That
  check requires a shell and belongs with it.

## Evidence discipline

Every check is paired with a mutation it must reject, in
`crates/tokens/src/audit/tests.rs`. Each row was confirmed by deleting the check
it targets and observing the table go red — a deletion sweep, run because WP-020
found a gate in `generate` that was load-bearing on nothing and kept 74 tests
green when removed.

| Check deleted | Mutation table |
| --- | --- |
| `check_color_vision` | FAILED — "'reversible' and 'destructive' become the same colour" was accepted |
| duplicate icon/label detection | FAILED — "two roles share an icon and a label" was accepted |
| unknown-role detection | FAILED — "channels are declared for a role that does not exist" was accepted |

The colour maths is anchored outside this repository: black on white is WCAG's
published 21:1, a colour against itself is 1:1, and black against white is
delta-E 100 because CIELAB lightness runs 0..=100 by construction. The
colour-vision matrices are checked by their *defining qualitative property* —
red and green converge under protanopia and deuteranopia but not under
tritanopia, and greys are left untouched by all three — rather than by trusting
their digits, so a mistyped coefficient surfaces as a pair that failed to
converge instead of a plausible number with nothing to check it against.

## Traceability

How this package's `docs/traceability/` document is produced. Read by
`cargo xtask traceability`, which checks the declaration against the document it
describes in both directions: declaring `hand-maintained` while that file
carries the generated marker is refused, and declaring `generated` holds it to
byte equality with what the annotations produce.

```traceability
mode: generated
```
