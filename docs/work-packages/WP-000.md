## Owned paths

Machine-readable, and the single source of truth: `cargo xtask verify-ownership`
parses the block below, so the prose and the enforced data cannot drift apart.
`dir/**` means everything beneath `dir`. A path may be claimed by more than one
package — `tools/xtask/` genuinely is — and the checker reports overlaps rather
than forbidding them, because forbidding them would only push the sharing into
prose where nothing can see it.

```owned-paths
.cargo/**
.github/**
.editorconfig
.gitattributes
.gitignore
AGENTS.md
AGENT_BUILD_SPEC.md
CHANGELOG.md
CONTRIBUTING.md
Cargo.lock
Cargo.toml
LICENSE-APACHE
LICENSE-MIT
README.md
SECURITY.md
clippy.toml
deny.toml
rust-toolchain.toml
rustfmt.toml
docs/adr/**
docs/quality/**
docs/reviews/**
docs/spec-issues/**
docs/traceability/WP-000.md
docs/work-packages/WP-000.md
tools/xtask/**
```

### Generated paths

`Cargo.lock` is claimed above and stays WP-000's to *pin*. It is also generated,
and ownership of a generated file is really ownership of its inputs: every
package that adds a crate or a dependency rewrites it as a consequence of a
manifest it does own. Declaring it here lets `verify-change-ownership` accept
that consequence — **only** alongside a manifest the lockfile actually resolves.
A lockfile moving on its own is still refused for everyone but WP-000.

```derived-paths
Cargo.lock
```

`fuzz/Cargo.lock` is deliberately **not** declared. It sits inside WP-010's
`fuzz/**` and no other package has reason to carry it, and an exemption granted
before anyone needs it is an exemption nobody is checking. Declaring it is a
governance change on WP-010's document when that day comes.

## Assumptions

- GitHub Actions is the initial CI provider.
- GitHub-hosted runners are used without project-controlled builder
  containers. Fixed OS-version labels are used; any future builder container
  must be pinned by digest.
- The active GitHub CLI account `nathan-mcbride54` is the initial CODEOWNER.
  Ownership must be split into narrower teams as work packages gain dedicated
  maintainers.

## Out of scope

- Domain models and public schemas (WP-010)
- Fixture generation and destructive-test interlocks (WP-020)
- Desktop shell and accessibility harness (WP-030)
- Any storage discovery or mutation

## Verification and known gaps

*Moved here from `docs/traceability/WP-000.md` on 2026-07-30, when that file
became generated output. A generator cannot write narrative, and one that
overwrote this would have destroyed the most honest content in the
repository — so it lives in the document this package owns and a human
edits. The evidence **table** is generated from annotations and typed evidence
declarations; what the evidence does not establish is below.*

### Verification

The local evidence command is `cargo xtask ci`. The supply-chain command is
`cargo xtask supply-chain` after installing the pinned tools. Neither command
contains privileged or destructive storage behavior. No WP-000 command
enumerates, opens, or writes a block device. Its filesystem reads are all of
repository-controlled text: workflow and composite-action YAML for the
action-pin check, `Cargo.toml`/`package.json` and `cargo metadata` output for
the licence check, the `owned-paths` blocks and `git ls-files` for the ownership
check, both lockfiles, and `.cargo/config.toml`. An earlier version of this
document said `.github/workflows/` was the only read, which stopped being true
as each gate was added.

### Known gaps carried into later work packages

- Section 11.7 requires `docs/traceability/` to be generated by CI.
  **WP-000, WP-010 and WP-030 now are; WP-020 is not** (issue #39).

  What holds for WP-000: behavioural evidence is annotated beside tests;
  configuration, command, and aggregated evidence is declared as typed source
  data below. The vocabulary comes from requirement definitions, numeric
  headings, and the numbered operating-contract items that actually exist in
  the specification — not from a list this tool owns. Tests are checked against
  `cargo test -- --list`, paths against git and package ownership, and commands
  against xtask's parser. **A hand edit to the generated file fails CI.**
  Which package an annotation's evidence belongs to is answered from the
  `owned-paths` blocks; where a path is shared — as `tools/xtask/**` is, three
  ways — the annotation must say, and the declaration is checked against
  ownership rather than believed.

  Each package declares its own mode in a ```` ```traceability ```` block in its
  own document, and the declaration is checked **in both directions**: declaring
  `hand-maintained` while the file carries the generated marker is refused, so a
  stale exemption cannot outlive the conversion, and declaring `generated` holds
  the file to byte equality. A package declaring nothing is refused outright.
  Those four declarations are the honest measure of how far this has got.

  *The declaration started life as a constant in `tools/xtask` and was moved
  here, because WP-010 does not own that path and could therefore never have
  converted itself — the rollout would have been blocked by the ownership rule
  it exists to respect. Found by working out what increment 3 would have to do.*

  **The first generated version lost evidence; the current version does not
  silently absorb that loss.** The hand-written table carried 31 evidence rows
  and the first generated version carried 13. Numeric section references now
  resolve only when the heading or the numbered Section 1 contract item exists,
  and the typed declaration below gives non-test evidence a validated source.
  `docs/reviews/WP_000_TRACEABILITY_MIGRATION_2026-07-30.md` records a
  disposition for every old row. Generated row count is not the proof:
  zero unexplained relationships in that ledger is.

  What does **not** hold yet: WP-020 is still hand-written and can still drift
  exactly as before. WP-010 and WP-030 have completed their package-owned
  conversions with zero-loss migration ledgers. The remaining conversion is
  dependency-ready and belongs to WP-020 rather than to WP-000 — a package's
  traceability should be generated from evidence that package owns, not from a
  central authority's view of it.

  An annotation also **names the test it documents**, and the redundancy with
  the function beneath it is the mechanism rather than an oversight. Binding is
  positional, so on its own it cannot notice that its test was renamed or
  deleted — measured: the first version stayed green through a rename. With the
  name written out the two sources can disagree, so a rename, a deletion that
  slides an annotation onto its neighbour, and an annotation adrift above a
  helper are all refused. It landed before increment 3 because adding one line
  to the small initial annotation set was cheaper than repairing a repository-
  wide rollout, and the rollout is exactly when a mis-bound annotation becomes
  likely.
- Section 1.10 states that CI enforces path ownership via CODEOWNERS. GitHub
  CODEOWNERS requires review from an owner; it does not reject a diff that
  touches paths outside the work package's assignment. **Half closed
  2026-07-29:** the machine-readable data now exists — an `owned-paths` block in
  every `docs/work-packages/WP-*.md`, which is the same text a reviewer reads,
  so prose and data cannot drift — and `cargo xtask verify-ownership` runs
  inside `cargo xtask ci`, refusing a tracked file no package claims and a claim
  matching no file. All tracked files are claimed; `cargo xtask verify-ownership` prints the current count rather than this document restating a number that goes stale the next time a file is added.

  **The other half closed 2026-07-30.** `cargo xtask verify-change-ownership
  --base <rev>` requires every **non-merge** commit to carry a real
  `Work-Package:` git trailer and refuses any changed path outside that
  assignment. *An audit the same day found that this sentence had been written
  ahead of the code: the first version unioned the trailers of the whole range,
  so one declaring commit covered every undeclared commit beside it, and it
  matched any line beginning with the key rather than a trailer. Both are fixed;
  the sentence is now true, and the qualifier "non-merge" is load-bearing rather
  than a hedge — see the merge-commit row below.* Two design choices carry the
  weight:

  - The declaration is a **commit trailer**, not a branch name or a label. This
    repository's branch names are inconsistent (`work/audit-round-four` sits
    beside `work/wp-020-held-root`), so keying on them would have been a guess
    dressed as a rule; trailers are already used here, need no API call, and stay
    in the log permanently.
  - The catalogue is read from the **base revision**, so widening your own
    `owned-paths` block in the same change buys nothing. That was the specific
    hole the audit named in the inventory-only check.

  A `Governance: <reason>` trailer permits editing the assignments themselves and
  then **only** `docs/work-packages/WP-*.md` may change, so the trailer cannot
  carry code past the check it sits beside.

  Still a review obligation, and not automatable: sub-file grants. WP-030 owns
  "its own status rows" in `README.md`; a path checker sees the whole file.

  **A worked example of that gap, recorded rather than hidden.** PR #47 was a
  nominal WP-000 change (the action scanner) that also edited
  `docs/work-packages/WP-020.md` and the WP-010, WP-020 and WP-030 traceability
  files, all owned by those packages. The inventory check passed, because every
  path was claimed by *someone*. The second follow-up audit caught it by reading.

  Those edits were audit-driven corrections to false claims, which is a
  legitimate need and a category the ownership model has no route for: a
  correction to WP-020's record is WP-020's territory, but leaving a known-false
  safety claim standing until that package is next active is worse. **The fix is
  not to widen WP-000's claims** — that is precisely the "widen your own block
  and pass against the widened tree" move issue #39 warns about. It is to give
  cross-package corrections an explicit governance route, which issue #39 now
  carries.
- Coverage floors are set at M1 per Section 11.8 and are therefore not
  configured here.
- ~~The project carries no license.~~ **Closed 2026-07-29.** ADR-0006 adopts
  `MIT OR Apache-2.0`; `[licenses.private]` is now `ignore = false`, so
  `cargo deny check licenses` checks the workspace's own crates against the same
  allow-list as every dependency. SEC-005's inventory is satisfiable.

  ~~Two declarations remain outside that gate.~~ **Closed 2026-07-29.**
  `cargo xtask verify-licenses` walks every `Cargo.toml` and `package.json` and
  fails unless each declares `MIT OR Apache-2.0`; it runs inside
  `cargo xtask ci`, and its own mutation test removes a key and watches it
  refuse.
- SEC-010 requires builder images pinned by digest. GitHub-hosted runner labels
  cannot satisfy this, and the deviation is now **documented with its residual
  risk** in `docs/quality/dependency-policy.md` rather than implied to be
  compliance. It re-opens as a hard requirement when release builds exist
  (ADR-S1, Section 19).
- The release-tag comment on action pins is format-checked, but nothing
  verifies the tag resolves to the pinned SHA; recorded in
  `docs/quality/dependency-policy.md` as a review obligation on every bump.


## Traceability

How this package's `docs/traceability/` document is produced. Read by
`cargo xtask traceability`, which checks the declaration against the document it
describes in both directions: declaring `hand-maintained` while that file
carries the generated marker is refused, and declaring `generated` holds it to
byte equality with what the validated evidence sources produce.

```traceability
mode: generated
```

Evidence that is not naturally owned by one test is declared below as typed
source data. `cargo xtask traceability` validates every requirement against the
specification, every path against git and this package's `owned-paths`, every
test against the compiled test list, and every command against xtask's parser
before it renders the generated document.
