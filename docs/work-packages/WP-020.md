## What increment 1 delivers

`cargo xtask fixtures` writes eight synthetic images into `tests/generated/`,
which `.gitignore` excludes, because Section 16 forbids committing binary disk
images and Section 11.3 requires they be generated by script and cached.

Every image is a pure function of the code that builds it: no clock, no random
source, no environment. Two machines produce byte-identical output, which is
what lets a fixture be pinned by digest instead of committed.

The catalogue is chosen against requirements rather than for coverage's own
sake, and each entry records the requirement it serves:

| Fixture | Why it exists |
| --- | --- |
| `blank-512` | PART-001 initializes blank media; ADR-C3 makes a positively observed absent table a *determined* state |
| `gpt-basic-512` | INV-003 GPT detection, and the baseline every other fixture is compared against |
| `gpt-basic-4kn` | IMG-011: a 4Kn table is not a 512-byte table with different numbers |
| `mbr-basic-512` | INV-003 MBR detection; PART-010 converts between schemes |
| `gpt-corrupt-header-512` | ADR-C3 `Indeterminate`: a device that plainly claims a table whose table cannot be trusted |
| `gpt-missing-backup-512` | INV-003 inconsistent tables; PART-013 and REC-001 both reason about this |
| `hybrid-mbr-gpt-512` | INV-003 hybrid tables — one disk described twice by two schemes that can disagree |
| `apm-basic-512` | INV-003 Apple Partition Map, and every field is big-endian |
| `luks2-whole-disk-512` | FS-004 LUKS, LIN-003; whole-disk, which MODEL-002 permits |
| `lvm2-pv-orphan-512` | FS-004 LVM PV, and ADR-C5 `consumer: Null` — a member whose aggregate is not observed |
| `mdraid-1.2-member-512` | FS-004 Linux RAID, LIN-005; also an orphaned member |
| `ext4-with-stale-mdraid-090-512` | The multi-signature case: a live ext4 and an obsolete array membership on one device |

The three ADR-C3 table states are each represented, and a test asserts they stay
that way. Blank, present, and unreadable are three states, not two, and that
distinction is the whole point of ADR-C3.

## The SAFE-007 interlock

SAFE-007 requires a disposable-test token, a verified image or VM target, and an
explicit destructive-test profile — **all three** — and states that a single
environment variable is not sufficient proof.

| Factor | How it is supplied | Why it cannot be faked |
| --- | --- | --- |
| Profile | `--profile destructive` on the command line | Not read from the environment, so it cannot be inherited by accident from a parent shell |
| Token | `PARTMAN_DISPOSABLE_TOKEN`, matching the generated manifest | Derived from the fixture set's digests, so it cannot be known without having generated that set |
| Verified target | Every target is re-read and re-hashed | The bytes must equal an image this repository generated |

**Disposability is computed, never declared.** No caller may assert that a target
is safe to destroy. A block device cannot pass, and neither can a user's disk,
because neither will ever hash to a generated fixture. A target must also be a
regular file — checked without following symlinks — and must resolve inside the
fixture root, so `..` traversal and a symlink aimed at a device are both refused.

**Every failure is a refusal.** An unreadable manifest, an unresolvable path, a
missing file: all return a refusal, never a pass. SAFE-005 requires failing
closed, and an interlock that failed open under an I/O error would protect
nothing on exactly the damaged systems where it matters most.

**An empty target list is refused.** "Every target was verified" is vacuously
true of no targets, and a suite that passed the interlock while naming nothing
would be claiming a proof it never made.

Authorization is returned as a value whose only constructor is the interlock
itself, so a future function that requires one cannot be called without the check
having run. "Did anyone check?" is answered by the type rather than by review.

## Tier 2 and Tier 3 still refuse, and that is not a placeholder

`cargo xtask test --tier 2 --profile destructive`, with a correct token,
evaluates the interlock and then **still refuses**, because no Tier-2 suite
exists yet. Increment 2 supplies the harness those suites need.

Reporting success for a run of nothing would be the fake success path Section 12
and Section 16 forbid, and it would be worse here than elsewhere: a green
destructive tier is exactly the signal someone would trust when deciding whether
the interlock works.

## Deviation from Section 4.3

Section 4.3's proposed layout places fixtures under `tests/fixtures/`. The
generator is a workspace library crate at `crates/fixtures/` instead, because
`tests/` has a reserved meaning to Cargo and a member crate underneath it reads
as an integration-test target. Section 4.3 is proposed rather than normative;
generated *output* still lands in `tests/generated/`.

## Out of scope

- Loop devices, `kpartx`, LVM, mdraid, and any privileged operation (increment 2).
- Real file systems inside the fixtures. These images carry partition tables, not
  formatted volumes; FS-004 detection fixtures arrive with the adapters that
  need them.
- The T3 hardware matrix (increment 3).

## Increment 1b: on-disk signatures, and what probing them established

FS-004 requires detecting LVM PV, Linux RAID, LUKS, BitLocker, ZFS pool members,
Storage Spaces, and LDM metadata, and ADR-C5 resolves that by materializing each
as its own node. Those nodes need fixtures, and **a fixture a real prober does
not recognize proves nothing** — so every signature writer is checked against
`libblkid` and `wipefs` rather than against this project's reading of a
specification.

That check earned its keep three times:

- **LVM2** was undetectable until its checksum was reproduced. `libblkid`
  verifies it, and it is not CRC-32 but a nibble-at-a-time variant with its own
  initial value. A label carrying `LABELONE`, the `LVM2 001` type string, and a
  zero checksum is detected as nothing at all.
- **mdraid 1.2** was listed by `wipefs` but rejected by `blkid -p` until the
  superblock checksum was added — a folded sum of little-endian words, not a CRC.
  The two tools disagreeing is itself the useful part: `wipefs` enumerates magic
  matches, `blkid` validates.
- **ZFS is deliberately absent.** `libblkid` declares a 64 MiB minimum size for
  its ZFS prober and skips it entirely below that. At 64 MiB, with the uberblock
  magic verified by hexdump at the documented offset in all four labels,
  `blkid -p` still reports nothing. Some further condition is required and **what
  it is has not been established.** The writer is kept, documented, and out of
  the catalogue rather than shipped as a fixture nothing recognizes.

### The question this answered

`ext4-with-stale-mdraid-090-512` exists to settle something two earlier
investigations could not. A 0.90 superblock lives in the last 64 KiB-aligned
block, so formatting the start of a device never removes it, and a device can
carry a current file system and an obsolete array membership at once.

On that fixture, `wipefs -n` reports **both** signatures. `blkid -p -o udev` —
the form udev's builtin uses, and therefore what an unprivileged client reads
from the udev database — reports exactly **one**, and it is the *stale* one:
`ID_FS_TYPE=linux_raid_member`. `ID_FS_AMBIVALENT` does not fire.

So an unprivileged client and a privileged helper can describe the same bytes
differently, and the client's description is the one that is out of date. That is
recorded against Part 5's asymmetry conclusion in `docs/spec-issues/README.md`,
and it is the kind of fact that is cheap to establish with a fixture generator
and expensive to guess wrong in a design round.
