## What increment 1 delivers

`cargo xtask fixtures` writes 13 synthetic images into `tests/generated/`,
which `.gitignore` excludes, because Section 16 forbids committing binary disk
images and Section 11.3 requires they be generated by script and cached.

Every image is a pure function of the code that builds it: no clock, no random
source, no environment. Two machines produce byte-identical output, which is
what lets a fixture be pinned by digest instead of committed.

The catalogue is chosen against requirements rather than for coverage's own
sake, and each entry records the requirement it serves:

| Fixture | Why it exists |
| --- | --- |
| `blank-512` | PART-001 initializes blank media; ADR-C3 makes a positively observed absent table a *determined* state |
| `gpt-basic-512` | INV-003 GPT detection, and the baseline every other fixture is compared against |
| `gpt-basic-4kn` | IMG-011: a 4Kn table is not a 512-byte table with different numbers |
| `mbr-basic-512` | INV-003 MBR detection; PART-010 converts between schemes |
| `gpt-invalid-primary-valid-backup-512` | INV-003 damaged metadata and REC-001 restore: the primary no longer checksums while the backup does, so the table stays positively determinable. Recoverable, and **not** `Indeterminate` |
| `gpt-conflicting-tables-512` | ADR-C3 `Indeterminate`, properly: two independently valid tables describing *different* partitions, so nothing can be positively determined |
| `gpt-missing-backup-512` | INV-003 inconsistent tables; PART-013 and REC-001 both reason about this |
| `hybrid-mbr-gpt-512` | INV-003 hybrid tables — one disk described twice by two schemes that can disagree |
| `apm-basic-512` | INV-003 Apple Partition Map, and every field is big-endian |
| `luks2-whole-disk-512` | FS-004 LUKS, LIN-003; whole-disk, which MODEL-002 permits |
| `lvm2-pv-orphan-512` | FS-004 LVM PV, and ADR-C5 `consumer: Null` — a member whose aggregate is not observed |
| `mdraid-1.2-member-512` | FS-004 Linux RAID, LIN-005; also an orphaned member |
| `ext4-with-stale-mdraid-090-512` | The multi-signature case: a live ext4 and an obsolete array membership on one device |

The three ADR-C3 table states are each represented, and a test **classifies the
bytes** rather than checking that some filenames exist. Blank, present, and
indeterminate are three states, not two, and that distinction is the whole point
of ADR-C3.

The table above listed a `gpt-corrupt-header-512` entry as the `Indeterminate`
case until 2026-07-29. That fixture was renamed and split in increment 1c,
because it was recoverable from its valid backup and so was not indeterminate at
all; the rows above are now read off the catalogue. Increment 1c corrected the
code and left this table describing the superseded set — which is exactly why a
progress review found the work package unusable as a dependency gate.

## The SAFE-007 interlock

SAFE-007 requires a disposable-test token, a verified image or VM target, and an
explicit destructive-test profile — **all three** — and states that a single
environment variable is not sufficient proof.

| Factor | How it is supplied | Why it cannot be faked |
| --- | --- | --- |
| Profile | `--profile destructive` on the command line | Not read from the environment, so it cannot be inherited by accident from a parent shell |
| Token | `PARTMAN_DISPOSABLE_TOKEN`, matching the generated manifest | **Weak, and known to be.** A pure function of source: identical on every machine building a given commit, and printed to stdout where CI captures it. It proves only that **the invocation presented the exact build-derived value** — anyone with the repository can compute it without running the generator, so it is not evidence of provenance. Accident friction, not a secret; see ADR-0007 |
| Verified target | Every target is re-read and re-hashed | The bytes must equal an image this repository generated. This is where SAFE-007's strength actually rests |

**Two things must be read before this section is relied on, and both used to be
buried below.** The token is not an independent factor, so SAFE-007's three
factors are effectively two. And `Authorization` carries a *pathname*, not the
file object that was verified, so **binding it to an open file handle is a
precondition of increment 2** rather than a later refinement.

**Disposability is computed, never declared.** No caller may assert that a target
is safe to destroy. A block device cannot pass, and neither can a user's disk,
because neither will ever hash to a generated fixture. A target must also be a
regular file — checked without following symlinks — and must resolve inside the
fixture root, so `..` traversal and a symlink aimed at a device are both refused.

**Every failure is a refusal.** An unreadable manifest, an unresolvable path, a
missing file: all return a refusal, never a pass. SAFE-005 requires failing
closed, and an interlock that failed open under an I/O error would protect
nothing on exactly the damaged systems where it matters most.

**An empty target list is refused.** "Every target was verified" is vacuously
true of no targets, and a suite that passed the interlock while naming nothing
would be claiming a proof it never made.

Authorization is returned as a value whose only constructor is the interlock
itself, so a future function that requires one cannot be called without the check
having run. "Did anyone check?" is answered by the type rather than by review.

**"Did anyone check?" is not the same question as "is it still the file that was
checked?", and only the first is answered.** `Authorization` holds canonical
*paths* and is `Clone`, so between the hash check and any future use another
process can replace the directory entry, and the proof can outlive the state that
made it true. There is no destructive consumer today, so this is not a live
exploit — it is a hard blocker on adding one, and the list of what increment 2
must do about it is under "carried into increment 2" below.

## Tier 2 and Tier 3 still refuse, and that is not a placeholder

`cargo xtask test --tier 2 --profile destructive`, with a correct token,
evaluates the interlock and then **still refuses**, because no Tier-2 suite
exists yet. Increment 2 supplies the harness those suites need.

Reporting success for a run of nothing would be the fake success path Section 12
and Section 16 forbid, and it would be worse here than elsewhere: a green
destructive tier is exactly the signal someone would trust when deciding whether
the interlock works.

## Deviation from Section 4.3

Section 4.3's proposed layout places fixtures under `tests/fixtures/`. The
generator is a workspace library crate at `crates/fixtures/` instead, because
`tests/` has a reserved meaning to Cargo and a member crate underneath it reads
as an integration-test target. Section 4.3 is proposed rather than normative;
generated *output* still lands in `tests/generated/`.

## Out of scope

- Loop devices, `kpartx`, LVM, mdraid, and any privileged operation (increment 2).
- Real file systems inside the fixtures. These images carry partition tables, not
  formatted volumes; FS-004 detection fixtures arrive with the adapters that
  need them.
- The T3 hardware matrix (increment 3).

## Increment 1b: on-disk signatures, and what probing them established

FS-004 requires detecting LVM PV, Linux RAID, LUKS, BitLocker, ZFS pool members,
Storage Spaces, and LDM metadata, and ADR-C5 resolves that by materializing each
as its own node. Those nodes need fixtures, and **a fixture a real prober does
not recognize proves nothing** — so every signature writer is checked against
`libblkid` and `wipefs` rather than against this project's reading of a
specification.

That check earned its keep three times:

- **LVM2** was undetectable until its checksum was reproduced. `libblkid`
  verifies it, and it is not CRC-32 but a nibble-at-a-time variant with its own
  initial value. A label carrying `LABELONE`, the `LVM2 001` type string, and a
  zero checksum is detected as nothing at all.
- **mdraid 1.2** was listed by `wipefs` but rejected by `blkid -p` until the
  superblock checksum was added — a folded sum of little-endian words, not a CRC.
  The two tools disagreeing is itself the useful part: `wipefs` enumerates magic
  matches, `blkid` validates.
- **ZFS is deliberately absent.** `libblkid` declares a 64 MiB minimum size for
  its ZFS prober and skips it entirely below that. At 64 MiB, with the uberblock
  magic verified by hexdump at the documented offset in all four labels,
  `blkid -p` still reports nothing. Some further condition is required and **what
  it is has not been established.** The writer is kept, documented, and out of
  the catalogue rather than shipped as a fixture nothing recognizes.

### The question this answered

`ext4-with-stale-mdraid-090-512` exists to settle something two earlier
investigations could not. A 0.90 superblock lives in the last 64 KiB-aligned
block, so formatting the start of a device never removes it, and a device can
carry a current file system and an obsolete array membership at once.

On that fixture, `wipefs -n` reports **both** signatures. `blkid -p -o udev` —
the form udev's builtin uses, and therefore what an unprivileged client reads
from the udev database — reports exactly **one**, and it is the *stale* one:
`ID_FS_TYPE=linux_raid_member`. `ID_FS_AMBIVALENT` does not fire.

So an unprivileged client and a privileged helper can describe the same bytes
differently, and the client's description is the one that is out of date. That is
recorded against Part 5's asymmetry conclusion in `docs/spec-issues/README.md`,
and it is the kind of fact that is cheap to establish with a fixture generator
and expensive to guess wrong in a design round.

## Increment 1c: corrections from the project review

`docs/reviews/PROJECT_REVIEW_2026-07-28.md` found that two of increment 1's
central claims were not true of the code that made them. Both are corrected here,
and both were reproduced before being fixed.

### The interlock's root of trust was a user-writable file

Increment 1 said "disposability is computed, never declared." It was not. The
digest comparison was real, but the *expectations* came from
`tests/generated/MANIFEST` — a plain file in the very directory being verified —
and `Manifest::parse` accepted its token without checking that the token followed
from its own entries. Writing a manifest that named an arbitrary file's digest,
with any well-formed token, authorized that file. This was demonstrated end to
end before the fix.

Two changes close it:

- **Expectations now come from the compiled catalogue** (`catalogue::expected`),
  computed with no I/O. Generation is deterministic, so the expected digests are
  a pure function of the code in the binary. Nothing written to the fixture
  directory can change what the interlock expects — only what is on disk to be
  compared against it. `authorize` no longer accepts a caller-supplied manifest
  at all.
- **Targets are verified by name, length, and digest** against the entry for
  that name. Membership by digest alone was too weak: it admitted any file so
  long as *some* entry anywhere shared its digest.

`Manifest::parse` additionally recomputes the token from the parsed entries and
rejects a mismatch, so a forged manifest is refused wherever it is read, not only
on the interlock path.

This also largely closes the hard-link vector the review raised separately: a
link can now only pass if the file it points at already contains exactly a
fixture's bytes, and destroying that is not a loss. A `nlink > 1` refusal is
added on Unix as defence in depth, because a second name is still a second thing
a destructive suite could reach. Windows exposes link count only through
unstable APIs, so the check is Unix-only and the content requirement carries the
guarantee on both platforms.

### The `Indeterminate` fixture was recoverable, and its test could not tell

`gpt-corrupt-header-512.img` flipped the primary header's CRC and left the backup
header valid and in agreement with the entry array. ADR-C3 defines
`Indeterminate` as a table that cannot be read or parses ambiguously; this one is
positively determinable from its backup. It was a good recovery fixture wearing
the wrong label.

The test that was supposed to catch this asserted only that three *filenames*
existed. It never parsed or classified anything, so it would have passed no
matter what the bytes contained — and the traceability record cited it as
evidence for ADR-C3's three states.

Corrected by:

- renaming the image to `gpt-invalid-primary-valid-backup-512.img`, under an
  honest "damaged primary, intact backup" rationale;
- adding `gpt-conflicting-tables-512.img`, where primary and backup are each
  independently valid and describe **different** partitions, so nothing about the
  table can be positively determined — which is what `Indeterminate` means;
- replacing the filename test with one that **classifies the bytes**, using an
  oracle that recomputes both header checksums independently of the code that
  wrote them.

### Regeneration now prunes withdrawn fixtures

`generate` documented that it replaced the directory contents but only
overwrote current names, so the withdrawn ZFS image survived in working trees. It
now removes files the current catalogue does not produce — but only in a
directory that already holds one of our manifests, so a mistyped root cannot
delete a user's files.

### What the remediation itself got wrong, and an honest note on the token

An independent audit of the review found that the first attempt at the
manifest fix **left a hole its own new tests did not catch.** Containment was
`starts_with(root)` while the name came from `file_name()`, so a byte-identical
copy at `<root>/sub/blank-512.img` satisfied the root check, the name lookup, the
length check, and the digest check simultaneously. It authorized. Verified, then
closed by requiring the resolved path to equal `root.join(name)` exactly — an
equality, not a prefix — with a regression test.

The lesson is the review's own: implementing a recommendation is not the same as
closing the hole it describes, and new green tests around a change prove nothing
about the case nobody thought of.

**The disposable-test token is not a secret.** Since expectations moved to the
compiled catalogue, the token is a pure function of source: identical on every
machine building this commit, computable with no I/O, and printed to stdout by
`cargo xtask fixtures` where CI captures it. Anyone who can read the repository
can derive it.

It proves that the invocation presented the exact build-derived value, and no
more. It cannot prove the operator ran anything: a pure function of public source
can be computed by anyone holding the repository. What it buys is accident
friction — a destructive run cannot be produced by ambient environment state
alone — and SAFE-007's strength here rests on the target verification, which is
computed from bytes and cannot be asserted, not on the token. A factor with
genuinely independent strength would have to be a
per-generation value that is not derivable from source, and that is a decision
increment 2 should make deliberately rather than inherit.

Windows link coverage is also absent: the `nlink` guard is Unix-only because
Rust exposes the Windows link count only through unstable APIs, and adding
`windows-sys` to a crate whose sole dependency is `sha2` is a dependency-policy
decision rather than a code change.

## Increment 1d: a fixture's purpose is computed, not asserted beside it

The review ranked "tests whose names are the safety claim" as the systemic
weakness here, and named the root cause exactly: **no test bound a catalogue
fixture's bytes to its rationale.** Every layout and signature test rebuilt its
own image from its own literals, so nothing connected the catalogue to the
requirements it claimed to serve.

That was reproduced rather than accepted. Two builders were mutated — the LUKS2
fixture reduced to a blank image, and the multi-signature fixture stripped of the
stale mdraid superblock that the Part 5 asymmetry finding rests on — and **all 64
tests passed.** No failure, no warning. The traceability record would have gone
on citing `luks2-whole-disk-512.img` for FS-004 while it held nothing but zeros.

`crates/fixtures/src/evidence.rs` closes it by applying this crate's own rule to
its fixtures. The interlock computes disposability from a target's bytes instead
of accepting an assertion; evidence computes a fixture's *purpose* the same way.
Each catalogue entry has a claim, checked from the bytes its builder produces:

- **Exhaustive in both directions.** A fixture with no claim fails the suite, and
  a claim naming no fixture fails it too. An unregistered name is a refusal, not
  "nothing to check" — the gap would otherwise return one new fixture at a time.
- **Every claim is proved capable of failing.** A check that accepts everything
  would pass a "does it satisfy its claim" test forever, which is the same defect
  one level up. Each fixture is paired with at least one mutation the claim must
  reject, and the pairing is exhaustive. Two of those mutations are the real ones
  above.
- **Generation enforces it.** `generate` verifies before writing, so an image
  that stopped serving its purpose never reaches disk. The refusal names what was
  lost rather than which assertion fired.
- **The oracles are independent of the writers.** A check that called the
  writer's own checksum would prove only self-consistency, so CRC-32 is
  reimplemented by table lookup against the writer's bit loop, LVM2's CRC bitwise
  against its nibble table, and mdraid's sum with an iterative fold. Each is then
  anchored outside this repository: CRC-32 to the published IEEE check value, and
  the other two to `libblkid`, which validates both before naming a format.

### Two documented claims were wrong, in both directions

`corrupt_primary_header_crc` still described itself as producing ADR-C3's
`Indeterminate` state, contradicting `write_conflicting_backup` in the same file,
which had already been corrected. The layout test repeated it. Both now say
*recoverable*, which is what the catalogue has said since increment 1c.

The other correction runs the other way. The response to the project review
recorded that `authorization_cannot_be_forged_outside_this_module` "reportedly
stays green with `verify_target`'s body short-circuited" — read as evidence the
interlock suite was blind to that mutation. **It was run, and it is not.** Ten
tests fail: traversal, subdirectory copies, modified bytes, wrong names, missing
targets, and mixed requests. The named test does stay green, because it asserts a
compile-time property rather than target verification, but nothing about the
suite around it was as weak as the note implied. "Reportedly" was the tell: a
claim recorded without being executed, in a document written about that exact
failure.

### The first version of this fix repeated the defect it was written to end

Increment 1d was put through an adversarial pass — three lenses, each trying to
break a different property — before it was proposed. It found the module
directionally right and its central claims overstated, which is the same failure
this work package keeps recording about itself.

**The gate was proven by nothing.** `generate` refused an image that failed its
claim, and that refusal was load-bearing on nothing: deleting the check kept all
74 tests green, because every test handed `generate` the real catalogue, which
satisfies its claims. Nothing ever exercised the refusal. A safety check no test
can reach is precisely what `evidence` exists to prevent, and it was sitting
inside the fix for it. Closed by splitting out `generate_from`, which takes a
fixture list, so a test can hand it a fixture that keeps a catalogue name and
loses what the name promises. Deleting the gate now fails that test.

**"Anchored outside this repository" was true of one checksum in three.** The
module claimed each reimplementation was anchored externally. For CRC-32 that was
executable — the published check value `0xcbf43926` is asserted. For LVM2's CRC
and mdraid's folded sum there was no pinned value anywhere: changing the initial
constant in *both* the writer and the oracle kept every test green while making
every fixture undetectable. Two implementations agreeing is the "two opinions"
the module's own documentation says is insufficient. Closed by pinning the three
checksum fields to the values `libblkid` 2.41 accepted on 2026-07-28, recorded
with their provenance.

**Ten claims accepted mutations that destroyed the fixture's purpose.** The
checks verified structure the builder always produces and skipped the fields that
carry meaning. The sharpest: `gpt-conflicting-tables-512.img` proved "two tables
that disagree" by comparing entry-array CRCs, and changing one character of a
partition *name* makes the CRCs differ while both copies describe byte-identical
extents — a disk where everything is determinable, still reported as ADR-C3
`Indeterminate`. Others let a partition run 100 MB past a 4 MiB device, let the
4Kn fixture carry the 512-byte arm's literal LBAs, let the ext4 half lose the
feature flags that make it ext4 rather than ext2, and let the LVM2 label declare
a sector it is not in — which `libblkid` skips, and which lies outside the CRC
span, so every checksum stayed valid.

**Two of the mutations proving claims could fail were themselves unsound.** They
tripped a different check than the one under test, so they proved nothing about
it. Every mutation now carries the phrase its refusal must contain, and the
mutations that need a valid checksum repair the one they disturb — otherwise the
checksum check fires first and the claim under test is never reached.

### Two fixture defects the pass found, as opposed to check defects

- **`gpt-missing-backup-512.img` had a backup.** It zeroed the last sector only,
  leaving 16 KiB of byte-identical backup entry array at LBAs 8159 to 8190, which
  any recovery tool that scans rather than seeking to the last LBA would find.
  The fixture now erases the whole backup copy, so it is what its name says.
- **The 512-byte and 4Kn baselines shared a disk GUID**, because both derived it
  from the literal `"gpt-basic"`. Two different media with one identity is a
  manufactured instance of exactly the collision SI-27 is trying to reason about.
  Found by a new catalogue-wide identity check, which no single-image claim could
  have seen, and fixed by labelling the 4Kn image separately. The fixtures
  *derived* from the 512-byte baseline keep its GUID deliberately: they are one
  disk in different states.

### What increment 1d does not close

`catalogue::expected()`, which is the interlock's root of trust, builds its images
with no I/O and deliberately does not call `evidence::verify` — the authorization
path must not acquire new failure modes. So evidence gates what reaches disk, not
what the interlock expects. Every supported path fails loudly first, but the
guarantee is procedural there rather than structural, and increment 2 should close
it when it revisits the token.

Two further findings from the pass are recorded and **not** fixed here:

- **The sandbox directories in these tests are fixed paths under the system temp
  directory**, so two concurrent `cargo test` runs of this crate collide. It has
  not been observed to flake, but the suite is flaky by construction and a
  safety-gate suite is the wrong place for that.
- **Claim substance cannot be checked mechanically.** A fixture can be added with
  a claim that only checks the image's length. What rules it out is the
  requirement that every fixture have a mutation its claim must reject *with a
  named reason* — a check that accepts everything fails that test — but this is a
  process guarantee resting on whoever writes the mutation, not a structural one.

## Carried into increment 2, as preconditions rather than follow-ups

A progress review on 2026-07-28 confirmed these are gates, not refinements.

1. **Bind authorization to the file object, not its name.** Delivered in two
   parts, and the first part was **not** sufficient — recorded here rather than
   smoothed over.

   Increment 2a bound the *post-open* checks to the handle, and the
   2026-07-29 follow-up audit then showed the binding began one step too late.
   `verify_target` resolved the path, then opened it a second time, and an open
   that follows links can leave the fixture tree between those two operations:
   replace `root/name` with a symlink to an out-of-root file holding the
   fixture's exact bytes, and every handle-based check accepts it. Increment 2a
   claimed a raced symlink was harmless because the object is verified after
   opening. That was wrong, and the reason is worth keeping:
   `object_verification_alone_cannot_prove_root_membership` demonstrates that
   the object checks accept an out-of-root file with fixture bytes — they
   establish fixture *shape*, and containment is not a property of content. A
   user's ordinary file may hold those bytes.

   **Increment 2c closes this on Unix. Windows remains open.**

   `Authorization` now holds the fixture directory as an object, and targets are
   opened relative to that handle by catalogue basename — `rustix::fs::openat`
   with `NOFOLLOW`, which needs no `unsafe` anywhere in this crate, so SAFE-009
   requires no exception and no adapter crate for the Unix half. There are no
   intermediate components left for anything to redirect.

   *Corrected 2026-07-30: this paragraph also claimed the directory handle
   "outlives the target handles because `Authorization` owns both". It does not —
   `into_targets(self)` moves the targets out and drops the root field before the
   caller uses them. Nothing depended on the claim, which is why the code needed
   no change when the claim did: containment is established at `openat` time and
   is a property of the returned descriptor, not something the directory handle
   maintains afterwards. The root is still held, for the narrower reason that no
   accessor is offered and a consumer therefore never receives a root path to
   reopen by name.*
   `swapping_the_fixture_root_directory_before_open_cannot_redirect_the_write`
   stages the audit's exact attack through the pre-open seam and compares the
   authorized handle's **inode** against the real fixture's, because the decoy
   holds identical bytes and content cannot tell them apart. Under 2b that
   assertion fails.

   **Windows still opens by pathname**, because the standard library exposes no
   safe handle-relative open and the `NtCreateFile` route needs FFI, which
   SAFE-009 permits only in an adapter/FFI/helper crate. The residual is the
   full F-02 finding on that platform: a swapped fixture-root directory can
   still redirect the open. `RootDirectory::open_child` says so where the code
   is. **Tier 2 must not be enabled on Windows until this is closed.**

   For the record, the history of this precondition — increment 2b closed only
   the final-component form: The second follow-up audit pointed out what `open(2)` documents
   plainly: `O_NOFOLLOW` constrains the *last* path component only, and
   intermediate components are still resolved through symlinks. So the attack
   moves up one level — rename the fixture root `R` aside, put a symlink at `R`
   pointing to an outside directory `E`, place `E/name` with the fixture's exact
   bytes, and `open("R/name", O_NOFOLLOW)` follows the intermediate `R` because
   `name` itself is not a link. The saved strings still satisfy
   `resolved == root.join(name)`, and handle metadata, link count, length and
   digest all pass. A destructive write then lands outside the fixture root.

   This is the same lesson as
   `object_verification_alone_cannot_prove_root_membership`, one directory up:
   matching bytes prove shape, never location. Closing it needs a *held root
   directory object* and a direct-child open relative to it — `openat`-style,
   with the basename from the catalogue — so that path resolution and the open
   stop being two operations with a gap between them. More `canonicalize` calls
   cannot fix it. What increment 2b did deliver:
   `O_NOFOLLOW` on Unix (from `libc`, because the value differs across Linux,
   macOS and the BSDs) and `FILE_FLAG_OPEN_REPARSE_POINT` on Windows, so a link
   at the target's *own* name is refused rather than traversed. A test seam fires between canonicalization
   and open, which makes the race *scheduled* rather than sampled:
   `a_symlink_swapped_in_before_open_is_refused` performs exactly the audit's
   substitution and requires a refusal, and
   `an_object_swapped_in_before_open_is_refused_on_every_platform` covers the
   seam where symlink creation needs a privilege CI cannot guarantee. Removing
   the seam fails those tests by name.

   Residual, and not claimed closed: **the Windows hard-link vector.** A hard
   link is not a reparse point, so no-follow does not refuse one, and the
   `nlink` guard is Unix-only because stable Rust exposes link counts on
   Windows only behind an unstable feature. That is precondition 3 below.

   **Do not enable Tier 2 on any platform until the held-root-directory open
   lands for that platform.**

   Also still true of increment 2a, and still the point: [`Authorization`] is
   non-cloneable (a `compile_fail` doctest pins this), consumed by
   `into_targets`, and carries open `File` handles: `fstat`, the hard-link
   count, the length, and every content byte are read **through the handle**,
   and the handle itself — the verified object — is what a destructive
   consumer receives. On Windows the handle's share mode refuses concurrent
   writes, deletion, and renames through any name, hard links included, for as
   long as the authorization lives; on POSIX, where no mandatory equivalent
   exists, the guarantee is that rebinding the name cannot change which object
   is held. The replace-after-authorization test demanded here exists on both
   platform families, and handle-purity is proven *deterministically*:
   `verify_object` takes no usable path, and its test deletes the path before
   verifying, so any check that regressed to a by-path read fails on a missing
   file rather than only during a race. Two regressions were planted to
   confirm the tests catch them (`stat`-by-path for `fstat`, `fs::read` for
   the handle read); both failed by name.

   The by-name `symlink_metadata` check is kept, but only as hygiene that gives
   symlinks their own readable refusal. It is raceable, and after increment 2b
   nothing safety-relevant rests on it.
2. ~~**Decide a genuinely independent token factor.**~~ **Closed 2026-07-29 by
   decision, not by code: [ADR-0007](../adr/0007-safe-007-third-factor.md).**

   The queued answer — "add an entropy source" — was wrong, and finding out why
   is the useful part. `authorize` deliberately trusts nothing inside the
   directory it verifies; expectations come from the compiled catalogue, because
   accepting a caller-supplied manifest was a defect that let a hand-written one
   authorize an arbitrary target. A per-generation random token **cannot** be
   compiled in, so the interlock would have to read it from the fixture root —
   re-creating exactly that trust dependency. An actor who can write the fixture
   root could write the token they intend to present. Randomness would add a
   dependency and a writable-file trust while defeating nobody.

   Read exactly, SAFE-007 requires the three factors to be *present* and forbids
   one environment variable from standing in for all of them. Both hold: the
   profile is a command-line argument, the target is verified from its own bytes
   against compiled expectations through a no-follow open, and the token is the
   only environment variable of the three. It does not require independence, and
   holding the code to a standard the specification does not set is what made
   this precondition unclosable. The token is an **operator-intent proof** —
   whoever asked for destruction ran the generator and copied a value out of its
   output. That is what the table above claims, and it is what the code does.

   A real third factor needs state outside both the source tree and the fixture
   root. That is a T2/T3 lab-architecture decision (Section 11.2, increment 3),
   and ADR-0007 records it as the revisit condition rather than guessing at it.
3. **Windows other-name coverage** for the `nlink` guard. **Ordinary work with a
   known route — not a blocked decision.** SI-36 was filed claiming SAFE-009 was
   ambiguous here and is **withdrawn**: SAFE-009 permits `unsafe` *only* in
   adapter, FFI, and helper crates, which forbids it in `crates/fixtures` and
   names the route in the same clause — a narrow platform-query adapter crate
   with a reviewed module, or a vetted safe dependency.

   The audit also sharpened what the residual actually is. `FILE_SHARE_READ`
   stops *competing* opens while an authorization lives; it does **not** make a
   pre-existing hard link safe, because the destructive consumer writes through
   the already-authorized handle and that write changes the file through every
   name, including an outside alias. So this is not merely a missing snapshot
   check.

   The toolchain measurement below stands: the check cannot be written with std
   alone.

   `MetadataExt::number_of_links` is unstable behind `windows_by_handle`
   (rust-lang/rust#63010), verified against 1.96.0, and nightly is a bounded
   exception for `fuzz/` alone. The remaining route is FFI, and SAFE-009's two
   lists — forbidden in "domain, planner, validator, journal, rpc", permitted in
   "adapter, FFI, and helper crates" — name `crates/fixtures` in neither. That
   is an enumeration rather than a rule, so it cannot be settled by reading
   harder; per Section 0.2 it is filed, not guessed.

   The residual is narrow and unchanged: while an authorization is held, the
   Windows share mode refuses writes through *any* name for the object, hard
   links included, so the exposure is the window between generation and
   authorization — during which a hard-linked impostor must still carry the
   fixture's exact bytes.

## Increment 1e: the last manual check, automated

The project review left one finding open here: **"real-prober acceptance is
manual, not regression-protected."** It was the last place in this package where
an important property rested on a person having looked once. Someone ran `blkid`,
read the output, and wrote a table into a document — and nothing re-read it.

That matters because increment 1d's evidence layer proves a fixture's *structure*
is what its rationale claims, which is necessary and not sufficient. A structure
this project believes is correct can still be one `libblkid` declines to name,
and two of the signature writers here were exactly that until their checksums
were reproduced. Neither the format documentation nor this crate's own tests
could have said so.

`cargo xtask probe` re-runs `blkid -p -o udev` and `wipefs -n` over every
generated fixture and compares against `crates/fixtures/src/prober.rs`. Both
tools are read-only and are handed regular files, never a device, so the check
stays unprivileged. It needs Linux, so CI runs it as its own job rather than
inside `cargo xtask ci`.

**The comparison is a chosen subset, deliberately.** `blkid` emits keys that vary
by version, and the fixtures are probed on at least two — 2.41 in development and
whatever `ubuntu-24.04` ships. Comparing the whole output would fail on a
toolchain upgrade rather than on a fixture regression, and a check that fails for
the wrong reason gets disabled rather than fixed. So it is exact over the format
name, identity, label, partition-table kind, and the **full set** of `wipefs`
signature offsets — compared in both directions, because a fixture quietly
gaining a signature is as much a regression as losing one — and silent about the
rest.

**The table is checked on machines with no prober too.** A verbatim capture of
the real 2.41 output is embedded in the tests, and the recorded expectations are
compared against it. Without that, the table would be a hand-written list only a
Linux CI job ever tested, and a transcription slip between the measurement and
the table would look exactly like a passing test. The comparison is also proved
capable of failing in all four directions: a format no longer detected, a changed
answer, a lost signature, and an added one.

### What the automation pinned down

Three rows are not what a reader would predict from the fixture's name, and each
now carries the reason so nobody "fixes" the fixture:

- `gpt-basic-4kn.img` reports **`PMBR`, not `gpt`** — file-based probing assumes
  512-byte sectors, so the 4Kn table at `0x1000` is never read. IMG-011 evidence
  cannot come from file probing at all; it needs a loop device with an explicit
  sector size, which is Tier 2.
- `gpt-conflicting-tables-512.img` is **byte-identical to `gpt-basic-512.img`**
  from both tools. That equality is SI-35, and it is now asserted rather than
  observed once: if `libblkid` ever separates them, the test fails and SI-35
  narrows.
- `ext4-with-stale-mdraid-090-512.img` reports the **stale** membership as its
  single answer while `wipefs` enumerates both. Part 5's asymmetry conclusion and
  SI-34 both rest on that, and it is now a test rather than a paragraph.

### Its first run falsified a claim increment 1 had recorded

The check earned its keep immediately, which is the strongest argument for having
built it. On `ubuntu-24.04` — util-linux **2.39.3** — `blkid -p` reports
**nothing** for `mdraid-1.2-member-512.img`, while `wipefs` still lists the
superblock at `0x1000` and both tools agree about every other fixture, including
the 0.90 superblock in the stale-pair image.

Increment 1 verified the signature writers by hand against `libblkid` 2.41 on one
machine and recorded the result as unconditional. It is not: **FS-004 Linux RAID
and LIN-005 are not established on the util-linux a stock Ubuntu 24.04 ships.**
A manual check on one machine cannot find that, and a table nothing re-reads
cannot report it.

The expectation is now version-keyed rather than relaxed. Below 2.41 the recorded
answer is *silence*, so a prober that starts naming the fixture fails just as one
that stops does, and the `wipefs` enumeration is still required on both. Neither
version's behaviour can drift unnoticed.

**The cause is unestablished and is recorded as such.** Both versions' checksum
routines are arithmetically identical, and the fixture satisfies the magic,
`major_version` and `super_offset` checks 2.39 documents. Finding the failing
condition needs a 2.39 environment to bisect against, which this project does not
have. `docs/quality/observability.md` records what was ruled out, in the same
posture as the ZFS writer: the negative result is kept so it is not rediscovered,
and no mechanism is asserted without measuring it.

### What increment 1e does not close

`libblkid` is one prober. macOS and Windows have their own, this establishes
nothing about either, and the `docs/quality/observability.md` gaps for those
platforms are unchanged. BitLocker, Storage Spaces, LDM and a recognized ZFS
member still have no fixtures, so the FS-004 rows they would occupy are absent
from the table rather than failing in it — an expectation cannot regress for a
fixture that does not exist.

## Increment 1f: the fail-open edges, including one increment 1e introduced

A progress review found two fail-open paths and one flaky-by-construction test
harness. The first is the sharpest, because it is a defect increment 1e created
in the module increment 1d wrote about.

**The prober parsers discarded what they could not read.** `parse_wipefs` used
`filter_map` and `parse_udev` silently dropped any line without `=`, so a row a
parser could not read was **not** an "unexpected signature" that `compare` would
report — it was *no observation at all*. On `blank-512.img`, whose expectation is
nothing, an entirely changed output shape parsed as empty and passed. Meanwhile
the module's own documentation claimed the signature set was "compared in **both**
directions". Increment 1d exists to end claims that outrun their code, and this
one was written one increment later, in the module documenting that rule.

The test beside it, `the_parsers_read_the_shapes_the_tools_actually_emit`, fed
the parsers only valid output. Increment 1d had just established that every claim
needs a case proving it can fail; that rule was not applied one module over.

Both parsers now return `Result` and refuse a line with no `=`, an empty or
repeated key, a non-hexadecimal or unprefixed offset, a row naming no type, a
header anywhere but the first line, and a repeated row. `probe_output` no longer
uses `from_utf8_lossy`, because substituting U+FFFD hands the parser a line the
tool did not emit. Genuinely empty output is now the only route to an empty
observation.

**Directory ownership was inferred from a filename.** Pruning was guarded by
`root.join(MANIFEST_FILE).is_file()`, which establishes nothing about who wrote
the file and follows a symlink besides. Any directory holding an unrelated
regular file — or a link — named `MANIFEST` was treated as ours and could lose
its other regular files. The regression test covered only a directory with *no*
manifest, so it proved less than its name said.

Ownership is now computed, the same rule the interlock applies to a destructive
target: a regular file reached without following a link, whose contents parse as
one of our manifests, with `Manifest::parse` recomputing the token from the
entries so a hand-written file cannot claim ownership either. Every failure is a
refusal to prune.

**The sandboxes were flaky by construction.** Catalogue and interlock tests used
fixed paths and deleted them at setup and drop, so two concurrent `cargo test`
runs of this crate erased each other's fixture trees — in the suite that gates
destructive execution. Each directory now carries the process id and a
per-process counter.

Each of the three fixes was verified by reverting it and confirming the new tests
fail: the old ownership guard fails
`a_foreign_file_named_manifest_does_not_authorize_deletion`, and a `filter_map`
parser fails both `a_line_the_parser_cannot_read_is_refused_rather_than_dropped`
and `a_changed_output_shape_cannot_pass_as_a_blank_fixture`.
