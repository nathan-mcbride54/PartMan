- Spec version: 4.0.0
- Stage: Foundations (M0)
- Objective: Generate synthetic and golden disk images by script, and implement
  the SAFE-007 interlocks that stand between a destructive suite and anything it
  might write to.
- Requirement IDs: SAFE-001, SAFE-002, SAFE-004, SAFE-005, SAFE-007, SAFE-009,
  INV-003, IMG-011, Section 11.3, Section 16

  2e additionally registers the narrowly scoped Tier-2 non-destructive,
  logical-content-read-only Linux-VM loop-control acceptance described below.
  The repository task runner may execute only that named acceptance under
  SAFE-001, SAFE-002, and all SAFE-007 factors. It exercises the existing
  `--profile destructive` factor solely to obtain the interlock's verified
  handle; no destructive suite or storage-writing operation is registered, and
  every request for either continues to refuse

### Increment 2e authorization boundary

Increment 2e may create `crates/ffi-linux-loop` and the narrowly associated
WP-020 tests, fixtures, xtask harness, traceability, status-row, changelog, and
`docs/quality/test-tiers.md` updates required to close repository issue #94.
The implementation change may enable only this exact named non-destructive,
logical-content-read-only Tier-2 Linux-VM loop-control acceptance in the tier
runner:

```text
cargo xtask test --tier 2 --profile destructive --acceptance linux-loop-read-only
```

That acceptance exercises the existing `--profile destructive` factor solely
to obtain the interlock's verified handle. Every generic destructive Tier-2
request and every Tier-3 request must continue to refuse; no destructive suite
or storage-writing operation is registered.

The crate exists solely to provide a safe, descriptor-bound Linux loop-device
boundary. Its low-level safe API accepts an `AsFd` backing object, never a
backing pathname, and narrowly supports loop configuration,
`LOOP_GET_STATUS64` read-back and identity verification, rejection or detection
of rebinding including `LOOP_CHANGE_FD`, and descriptor-bound detach. It may not
expose a generic ioctl facility, arbitrary command execution, a product storage
adapter, or pathname-based attachment.

The only WP-020 harness entry point may not accept a caller-selected descriptor.
It consumes the still-live SAFE-007 `Authorization`, consumes exactly its two
selected `VerifiedTarget` values, and passes those exact held `File` objects to
the FFI boundary. A structural or call-site test must make an unverified descriptor
unable to reach loop attachment through the harness. The end-to-end acceptance
chain is: authorize both fixtures with every SAFE-007 factor; hash both exact
held objects and require each digest to match the compiled fixture catalogue
before any attach; configure from the selected held backing
descriptor; assert that `LOOP_GET_STATUS64`'s `(lo_device, lo_inode)` equals
`fstat`'s `(st_dev, st_ino)` from that descriptor; hold the backing and
loop-device descriptors across use; open the kernel-selected `/dev/loopN` only
from the number the kernel returned; record the held node's filesystem device,
inode, and `rdev`; probe with an in-process positional read through that held
descriptor; repeat the backing, configuration, and held-node comparisons after
the probe; issue `LOOP_CLR_FD` through the held descriptor; require
`LOOP_GET_STATUS64` to report `ENXIO`; drop the held loop `File`; and boundedly
require the exact retained-rdev `/sys/dev/block/M:m` root to be readable, not
itself contain a `partition` attribute, and have no immediate child containing a
`partition` attribute before treating teardown as complete. A missing,
unreadable, ambiguous, or retry-exhausted state is a cleanup-uncertain refusal
that requires discarding or reverting the VM. The ordinary leg and the
adversarial `LOOP_CHANGE_FD` leg both follow that cleanup rule; the adversarial
leg discards its pending bytes when the expected backing mismatch is detected.
Only after both legs have confirmed that full teardown are both held fixture
objects hashed again, and only unchanged hashes release a success observation.
No backing-path or loop-device-path reopen may substitute for any link in that
chain. The internal device-name hop remains recorded rather than claimed as
handle-relative path resolution, and no external consumer receives it. A
`LOOP_CONFIGURE` `EBUSY` refuses immediately, without retry, because isolated
loop state was not established; bounded retries exist
only in cleanup, where ordinary kernel/udev discovery is permitted.

The digest and status comparisons are sampled and cannot defeat an ABA change
entirely between samples. External run evidence must exclude every other actor
able to modify either fixture and every other actor able to administer or
rebind loop devices. Ordinary kernel/udev read/open discovery is allowed and is
handled by bounded detach retries plus exact retained-rdev sysfs inspection. VM
isolation bounds consequences but does not itself prove the exclusions. The
result establishes no persistent fixture change or rebind under those
conditions, not continuous binding against a concurrent actor. A future
destructive path may not inherit that conclusion; it still needs the separately
proven pre-write discipline required below.

Increment 2e launches no external prober or other storage tool. Its probe is
part of the process that holds the verified backing and loop-device descriptors,
so no shell, `PATH` search, subprocess identity, or external pathname consumer
enters the evidence chain. SAFE-004's launch requirements remain unchanged for
every other command.

### Increment 2f authorization boundary

**Nothing in increment 2e's boundary above is amended.** Every sentence of it
remains true of increment 2e, including "launches no external prober or other
storage tool" and the rule that no external consumer receives the device-name
hop. Those clauses are the substance of an acceptance that has already been
measured and reviewed; rewriting them to make room for a later capability would
retroactively weaken a claim that was true when it was proved. Increment 2f is
a **separate, additional grant with its own terms**, and where its terms are
weaker than 2e's, that is stated here rather than absorbed silently.

Increment 2f exists for one reason, recorded on repository issue #130:
`docs/quality/observability.md`'s hardened non-WSL SI-35 protocol requires a
descriptor-bound setup program that holds the backing and loop-device
descriptors across an interval in which **external** `blkid`, `wipefs`, and
`udevadm` probes run. Increment 2e's entry point cannot serve that protocol —
it probes in-process and detaches before returning — and no distro ships a
substitute, because `losetup` resolves its path argument in userspace, which is
the exact gap issue #94 named.

**The capability granted.** Increment 2f may add to `crates/ffi-linux-loop` a
second entry point providing a hold-open session: configure from a held
verified backing descriptor, verify, run a bounded sequence of external probes
against the live loop device, verify again, and detach under 2e's existing
confirmed-detach and partition-teardown discipline. It may launch a predeclared
external prober, which increment 2e may not.

**Why the crate, and not the caller, launches that prober.** A design that
lends the caller the loop-device descriptor or its node name was evaluated and
**rejected on measurement, not taste**: `BorrowedFd::try_clone_to_owned` is
safe, stable Rust, and the resulting `OwnedFd` outlives the borrow, the
supervised window, and the detach. Because `open_loop_node` opens the node
`O_RDWR`, one safe line in a caller-supplied closure would yield a writable
handle to the loop device that survives the crate's supervision entirely. A
scoped closure or RAII guard therefore does **not** confine the descriptor, and
this boundary does not pretend otherwise. Increment 2f consequently forbids
handing any loop descriptor, `BorrowedFd`, `OwnedFd`, device node name, path,
or device number to a caller, and requires the crate itself to own the launch.

**What remains forbidden, unchanged from 2e.** No pathname-based attachment:
configuration still comes only from the held SAFE-007-verified backing
descriptor. No caller-selected descriptor, file, path, loop number, or device
name is an accepted argument; 2f's entry point still consumes a live
`Authorization` and exactly its selected `VerifiedTarget` values. No generic
ioctl facility. No arbitrary command execution. The mapping still carries
`LO_FLAGS_READ_ONLY` and the session issues no logical write, discard, or zero
operation. No backing-path or loop-device-path reopen may substitute for any
link in the chain. No destructive suite is registered, and **no future
destructive path may inherit this grant**: 2f is read-only by construction, its
conclusion is not a pre-write discipline, and citing it as one is forbidden in
the same terms 2e uses.

**In-process verification reads the session may additionally take.** The
SI-35 instrument's gates 3, 6, and 7 need facts only the held descriptors can
supply, so the session may also read, in process and without launching
anything: the attached device's complete logical contents through the held
loop descriptor — hashed before the first and after the last external launch,
both required to equal the compiled catalogue digest; the named sysfs
projection fields from its retained-rdev root (disk size, read-only flag, and
logical block size; partition index, start, size, and read-only flag); and
the mount table, required to contain no session device number. The
predeclared udev query may run twice per node for the instrument's
byte-stability gate. These reads accept no caller input, address nothing by
name the session did not already derive, and surface only integers, booleans,
and equality facts; a mismatch, a mounted node, or a writable partition
refuses the session with nothing published.

**The launch controls the prober is subject to.** Every external executable is
predeclared by a compiled absolute path, is launched directly with structured
argv — no shell, no `PATH` search, no caller-supplied argument — with a
sanitized environment, bounded captured output, and a timeout, under the same
SAFE-004-derived controls WP-035's dependency doctor already applies. The
device node name reaches that launch and nothing else. While the device is
bound, the name is not returned, not logged to a caller-visible surface, and
not exposed through any public type. Captured prober output may quote the
name — `wipefs` prints the device it was given, and refusing that output would
refuse the evidence SI-35's gate 8 requires retained raw — so captured output
is quarantined inside the session while the device is bound and is released
only after confirmed detach and partition teardown, when the name no longer
designates the verified backing. No public type carries the name, path, or
device number as a field, and nothing the crate returns lets a caller reach
the loop device while it is bound.
Immediately before and immediately after every external call, the node's
`st_rdev` must equal the held loop descriptor's and the full
`LOOP_GET_STATUS64` backing/flags/geometry binding must be re-verified. Any
mismatch voids the session and publishes no observation.

**The residual 2f adds, stated plainly.** Increment 2e's probe was in-process,
so no other actor could reach the loop during it. Increment 2f deliberately
opens an interval in which a separate privileged process runs, and that
interval is as long as an external prober takes rather than a few in-process
reads. Across it, the `LOOP_CHANGE_FD` bracketing **detects a rebind that
happened; it does not prevent one.** The prober's identity rests on a compiled
absolute path and a recorded version, not on a verified executable digest.
A prober necessarily opens the device node itself, and the crate cannot
constrain what a separate process does with a descriptor it opened. **Increment
2f is therefore weaker than increment 2e, and no evidence produced under it may
be described as carrying 2e's strength.**

**Test obligations.** A compile-fail proof that 2f's entry point does not accept
a caller-selected `File` or descriptor. A structural test that no public
signature returns a descriptor, `BorrowedFd`, `OwnedFd`, device name, path, or
device number. A structural test that the prober launch reaches no shell and no
`PATH` lookup. A test that a rebind detected across the open window voids the
session and publishes nothing. A test that captured prober output is
unavailable to the caller until detach and partition teardown are confirmed. A
test that an error, panic, or signal inside the
open window still reaches confirmed detach, or refuses with cleanup uncertain.

**Sequencing.** This grant lands before the commit that first uses it, per the
granted-before-first-use precedent. WP-035's protocol additionally describes the
setup actor and the comparison actor as distinct; a crate-owned launch makes
them one process. That is a **mechanism amendment to a preregistered
instrument**, and WP-035 must record it in `docs/quality/observability.md`, with
its reasoning, **before any measurement output exists** — never afterwards, and
never as a way to fit the instrument to what was built.

Any `unsafe` exception is limited to the documented and reviewed
`crates/ffi-linux-loop/src/sys.rs` module under SAFE-009. The safe boundary owns
or borrows file descriptors with explicit lifetime rules and must prevent a
descriptor or loop-device identity from being silently substituted between
verification and use. The fixtures crate remains `unsafe_code = "deny"`. The
new workspace member must contain a crate-level `//!` documentation comment and
`[lints] workspace = true`.

Tier-1 evidence must cover request construction, response decoding, state
transitions, descriptor-lifetime behavior, rebinding refusal, failure mapping,
cleanup failure, and the rule that no observation becomes usable before final
verification and confirmed detach, without requiring a loop device. Closing
issue #94 additionally
requires the registered, privileged Tier-2 non-destructive,
logical-content-read-only loop-control acceptance to pass in a disposable
Proxmox-hosted non-WSL Linux VM. SAFE-001, SAFE-002, and all three SAFE-007
factors apply even though the selected operation makes no logical change to
backing-storage bytes. The run must prove the full chain above and include an adversarial
`LOOP_CHANGE_FD` leg; a change either is prevented by a documented privilege or
attachment-property boundary or causes final verification to discard every
observation and refuse. Any mismatch, changed fixture hash, or cleanup failure
refuses rather than returning usable evidence. A future destructive path must
make `LOOP_CHANGE_FD` inapplicable through read-write attachment or establish
another explicitly proven pre-write discipline. This acceptance does not
register or enable a destructive suite and does not weaken SAFE-007. Its use of
the interlock grants SAFE-007 coverage only to this named acceptance; it does
not extend that coverage to the product inspector or to a general read path.

WP-020 may establish the mechanism and close #94, but it may not record SI-35
platform conclusions in `docs/quality/observability.md`; that evidence remains
owned by WP-035.

### Increment 2g authorization boundary

gives the load-bearing sentence "no destructive suite is registered" a compiled

Increment 2g may add to `crates/fixtures` a compiled destructive-suite

The registry follows the catalogue pattern: compiled into the binary, nothing
read from the fixture root or any other file. A registered suite must state,
as data: its fixture set by catalogue basename; its verified target class — a
closed vocabulary whose only variant is the interlock-verified generated
fixture file; its per-fixture intended-change contract, the exact byte ranges
a run may change with each range's reason stated, everything outside them
pinned by digest bracket; and its teardown proof obligations, a closed
vocabulary. Closed vocabularies are pinned by exhaustive-match tests, so a new
variant is a visible reviewed edit.

**The shipped registry is empty, and a test pins the emptiness.** Registering
the first real suite is increment 2h's delivery, behind its own recorded
boundary and an operator-accepted VM sitting — and it changes the meaning of
every generic-refusal test, each of which must be re-read at that edit rather
than merely re-run. The suite the refusal tests exercise is compiled only into
tests, never into the shipped registry.

**SAFE-007's three factors gate execution unchanged.** The registry adds a
further condition — a compiled suite must exist and its contract must admit
the authorized targets — never a substitute for any factor. Admission consumes
the interlock's live `Authorization` (the handle-holding proof, not a path
list) and refuses: a target set that is not exactly the suite's declared
fixture set, a declared fixture the catalogue does not generate, an empty
fixture set, a contract permitting no change, a zero-length range, a range
extending past the fixture's generated length, and overlapping ranges.
Admission is not clonable and there is no way to keep it while extracting its
targets, for the same reason `Authorization` works that way. **No executor
exists in 2g**: nothing consumes an admitted suite, every generic destructive
Tier-2 request and every Tier-3 request continues to refuse — the generic
refusal now cites the compiled registry's count rather than prose — and the
two registered acceptance selectors are untouched. An operator remains in the
trigger path of anything a future slice runs; nothing here creates an
unattended trigger, which ADR-0007 names as a revisit condition.

**The bright line, binding 2g and 2h both:** no product write path, no
storage-tool invocation, no domain types, no plan or hash surfaces. The
mutation a future suite performs is harness-owned bytes through an authorized
handle, and the deliverable is that a Tier-2 destructive *test* can exist, not
that the product can write.

**The write path, and why `LOOP_CHANGE_FD` is inapplicable rather than
detected.** `crates/ffi-linux-loop` gains one third entry point under this
grant. It consumes the registry's `Admission` — never a caller-selected file,
descriptor, loop number, or path — and configures a **read-write** loop
attachment (no `LO_FLAGS_READ_ONLY`; autoclear and partscan unchanged) from
the held verified backing descriptor. The kernel's loop driver refuses
`LOOP_CHANGE_FD` on a read-write attachment, which is precisely the first
option the 2e record names for a destructive path ("make `LOOP_CHANGE_FD`
inapplicable through read-write attachment"). The adversarial leg therefore
inverts 2e's: mid-suite, with the write not yet issued, the harness attempts
`LOOP_CHANGE_FD` and requires the kernel's refusal; if the kernel accepts the
rebind, the run is void, nothing is published, and the record must say so.

**The pre-write discipline, stated as its own rather than inherited.** The 2e
record forbids a destructive path inheriting its conclusion, so 2h's chain
is, in this order: the held backing object's complete bytes hashed through
its own descriptor and required to equal the compiled catalogue image the
contract names — in-crate, not inherited from the interlock's identical
earlier check; the declared range read through that descriptor and required
to **differ** from the contracted replacement, so the run can establish a
change rather than an equality that a never-written range would also satisfy;
the digest bracket over every byte outside the declared range; then attach,
full `LOOP_GET_STATUS64` identity binding verified against the held backing
descriptor, and the adversarial rebind refusal above; then the write —
exactly the contracted eight bytes at the contracted offset, through the held
loop-device descriptor, followed by `fdatasync` on it; identity re-verified;
descriptor-bound detach and partition teardown under 2e's confirmed
discipline; and only then, through the still-held backing descriptor: the
declared range must equal the contracted replacement bytes exactly, and the
outside-bracket hash must be unchanged. Any mismatch, unexpected kernel
acceptance, cleanup failure, or ordering violation refuses with nothing
published.

**Restoration is the runner's, and it runs on every outcome.** The final
teardown obligation — the backing file regenerated and re-digested to the
compiled catalogue — is discharged after the crate returns, on refusal as
well as on success, because every refusal reachable after the contracted
write leaves the fixture mutated and an early return would strand it that
way. Regeneration alone does not discharge it: `catalogue::generate` returns
a manifest computed from the images it built in memory and
`catalogue::expected()` is that same pure function, so comparing them
compares a function with itself and is true whatever is on disk. The
obligation requires `catalogue::verify_on_disk`, which re-reads every image
and re-hashes it. That check establishes the files' content, not durability —
the read may be served from the page cache — and the record must not claim
more. If restoration fails, no result is reported and the VM must be
discarded or reverted.

### The exclusions the acceptance requires, and how each was established

- **No other loop administrator.** The stock Ubuntu cloud image ships `snapd`,
  which held four squashfs loop devices at first boot. `snapd` and `udisks2`
  were purged and their trees removed; `losetup -a` was empty before every run.
  **This is a deliberate deviation from a stock image**, recorded rather than
  hidden, because the exclusion cannot hold while snapd runs. One residual: the
  unit `snapd.mounts-pre.target` still reports active while being `not-found` —
  no unit file and no binary remain, so it can mount nothing.
- **No other actor able to modify either fixture.** `/root` is `drwx------`
  root-owned, as is the fixture directory. The five non-root processes are
  stock daemons (`systemd-timesyncd`, `systemd-networkd`, `systemd-resolved`,
  `dbus-daemon`, `rsyslogd`); each one's `CapEff` was read from
  `/proc/<pid>/status` and none holds `CAP_SYS_ADMIN` (bit 21), so none can
  administer a loop device either.
- **Sole operator.** One authorized SSH key; `root` the only account with a
  usable login shell; the cloud-init account locked to `nologin` and its
  processes killed before the cited run.

### What this run does not establish

- **The guest was not network-isolated.** It held a DHCP address and a default
  route throughout, and this is recorded as a fact in the transcript rather
  than claimed away. The acceptance requires guest isolation and actor
  exclusion, not an air gap; no attempt is made to convert connectivity into a
  stronger claim than the evidence supports.
- Digest and status checks remain **discrete samples**. They cannot defeat an
  ABA change between samples, exactly as the increment's own limits state.
- VM isolation bounds consequences; it does not by itself prove the exclusions
  above. The exclusions rest on the enumerated facts, not on being a VM.
- A pass here is **not** a continuous-binding guarantee and grants no coverage
  to the product inspector or to a general read path. A future destructive path
  needs a separately proven pre-write discipline and may not inherit this
  conclusion.
- Nothing here registers a destructive suite. Increment 2's own scope remains
  unbuilt.

### Operational precondition discovered by the run

The acceptance runs `cargo xtask ci` first, and WP-035's
`no_output_in_any_mode_carries_an_environment_value` compares **every**
environment value of six characters or more against CLI output. Two runs failed
before the acceptance was reached: once on an injected `CIUSER=partman`, once on
the `SUDO_USER=partman` that `sudo` sets by itself. Both were coincidental
collisions — `partman` is the program's own name and appears in `help` output —
not leaks, and the tripwire behaved correctly in both.

**Run this acceptance as root over a direct login, with no `sudo` in the chain
and no injected variables, and do not name the VM's user, host, or any whole
path component something that appears in CLI output.** Adding an exemption to
the test instead would have edited the very commit under proof.

The 2026-08-11 retake hit the one collision that rule cannot dodge: the sweep
now checks identity-bearing variables at a three-byte floor, `root` cannot be
renamed, and static output had since gained the udev caveat's "root's udevd".
There the exemption **was** the remedy — the test names it for verified
coincidences — and it was landed as its own reviewed commit (PR #243) with the
acceptance then re-taken on the merged tree, so the exemption never rode the
commit under proof.

### The claim this run does and does not establish

- **It establishes that the kernel refuses `LOOP_CHANGE_FD` on a read-write
  attachment.** That was an assumption about the loop driver when the code was
  written and the review said so; it is now a measurement on kernels
  5.15.0-187-generic and 5.15.0-186-generic, and since the re-take the refusal
  is classified from an observed status re-read (issue #248) rather than from
  the errno alone. It is *not* a claim about every kernel, and the suite
  keeps the leg rather than deleting it precisely so a kernel that behaves
  differently voids the run instead of passing it.
- **It establishes that one contracted range changed and nothing else did**,
  by a digest bracket over every other byte of the backing object, taken
  before the write and re-checked after confirmed detach.
- It does **not** establish that the product may write. No product write path,
  no storage-tool invocation, no domain types, and no plan or hash surfaces
  were involved; the mutation is harness-owned bytes through an authorized
  handle. The deliverable is that a Tier-2 destructive *test* can exist.
- Digest and status checks remain **discrete samples** and cannot defeat an
  ABA change between them, exactly as 2e's limits state.
- Restoration is verified by re-reading the regenerated files, which
  establishes their content and **not their durability**: the read may be
  served from the page cache.

### The provisioning defect this sitting found

The runbook's `02-guest-provision.sh` runs
`apt-get purge -y snapd 2>/dev/null || true`, which discards both the purge's
error output and its exit status. On this guest the purge failed — snapd's
squashfs mounts, and therefore its loop bindings, were still live — and the
script continued. It aborted only incidentally, when the following
`rm -rf /snap` hit a read-only filesystem. Had that `rm` succeeded on a
partially unmounted tree, provisioning would have reported success **with
snapd still installed**, and the sitting would have recorded the
no-other-loop-administrator exclusion as established when it was not.

The exclusion is established by `losetup -a` being empty *and* snapd being
absent, not by the purge having been invoked; and a loop table can be
momentarily empty while snapd is installed and merely idle. The guest was
recovered by unmounting the squashfs mounts, rebooting to clear the lazily
detached loops, purging with output visible, and confirming `dpkg -l snapd`
reports the package removed before provisioning was re-run. That is what the
recorded environment rests on for this sitting. The script itself is fixed in
the same change as this record, so the next sitting does not depend on someone
repeating the diagnosis.

## What increment 1 delivers

`cargo xtask fixtures` writes 13 synthetic images into `tests/generated/`,
which `.gitignore` excludes, because Section 16 forbids committing binary disk
images and Section 11.3 requires they be generated by script and cached.

Every image is a pure function of the code that builds it: no clock, no random
source, no environment. Two machines produce byte-identical output, which is
what lets a fixture be pinned by digest instead of committed.

The catalogue is chosen against requirements rather than for coverage's own

## The SAFE-007 interlock

SAFE-007 requires a disposable-test token, a verified image or VM target, and an
explicit destructive-test profile — **all three** — and states that a single
environment variable is not sufficient proof.

| Factor | How it is supplied | Why it cannot be faked |
| --- | --- | --- |
| Profile | `--profile destructive` on the command line | Not read from the environment, so it cannot be inherited by accident from a parent shell |
| Token | `PARTMAN_DISPOSABLE_TOKEN`, matching the generated manifest | **Weak, and known to be.** A pure function of source: identical on every machine building a given commit, and printed to stdout where CI captures it. It proves only that **the invocation presented the exact build-derived value** — anyone with the repository can compute it without running the generator, so it is not evidence of provenance. Accident friction, not a secret; see ADR-0007 |
| Verified target | Every target is re-read and re-hashed | The bytes must equal an image this repository generated. This is where SAFE-007's strength actually rests |

**Two things must be read before this section is relied on, and both used to be
buried below.** The token is not an independent factor, so SAFE-007's three
factors are effectively two. And `Authorization` carries a *pathname*, not the
file object that was verified, so **binding it to an open file handle is a
precondition of increment 2** rather than a later refinement.

**Disposability is computed, never declared.** No caller may assert that a target
is safe to destroy. A block device cannot pass, and neither can a user's disk,
because neither will ever hash to a generated fixture. A target must also be a
regular file — checked without following symlinks — and must resolve inside the
fixture root, so `..` traversal and a symlink aimed at a device are both refused.

**Every failure is a refusal.** An unreadable manifest, an unresolvable path, a
missing file: all return a refusal, never a pass. SAFE-005 requires failing
closed, and an interlock that failed open under an I/O error would protect
nothing on exactly the damaged systems where it matters most.

**An empty target list is refused.** "Every target was verified" is vacuously
true of no targets, and a suite that passed the interlock while naming nothing
would be claiming a proof it never made.

Authorization is returned as a value whose only constructor is the interlock
itself, so a future function that requires one cannot be called without the check
having run. "Did anyone check?" is answered by the type rather than by review.

**"Did anyone check?" is not the same question as "is it still the file that was
checked?", and only the first is answered.** `Authorization` holds canonical
*paths* and is `Clone`, so between the hash check and any future use another
process can replace the directory entry, and the proof can outlive the state that
made it true. There is no destructive consumer today, so this is not a live
exploit — it is a hard blocker on adding one, and the list of what increment 2
must do about it is under "carried into increment 2" below.

## One read-only Tier-2 acceptance; destructive Tier 2 and all Tier 3 refuse

`cargo xtask test --tier 2 --profile destructive`, with a correct token,
evaluates the interlock and then **still refuses**, because no destructive
Tier-2 suite exists. Every Tier-3 request also refuses. The sole exception is
the exact selector
`cargo xtask test --tier 2 --profile destructive --acceptance
linux-loop-read-only`: it runs the non-destructive, logical-content-read-only
acceptance defined above and nothing else.

Reporting success for a run of nothing would be the fake success path Section 12
and Section 16 forbid, and it would be worse here than elsewhere: a green
destructive tier is exactly the signal someone would trust when deciding whether
the interlock works.

## Deviation from Section 4.3

Section 4.3's proposed layout places fixtures under `tests/fixtures/`. The
generator is a workspace library crate at `crates/fixtures/` instead, because
`tests/` has a reserved meaning to Cargo and a member crate underneath it reads
as an integration-test target. Section 4.3 is proposed rather than normative;
generated *output* still lands in `tests/generated/`.

- The T3 hardware matrix (increment 3).

## Increment 1b: on-disk signatures, and what probing them established

FS-004 requires detecting LVM PV, Linux RAID, LUKS, BitLocker, ZFS pool members,
Storage Spaces, and LDM metadata, and ADR-C5 resolves that by materializing each
as its own node. Those nodes need fixtures, and **a fixture a real prober does
not recognize proves nothing** — so every signature writer is checked against
`libblkid` and `wipefs` rather than against this project's reading of a
specification.

That check earned its keep three times:

- **LVM2** was undetectable until its checksum was reproduced. `libblkid`
  verifies it, and it is not CRC-32 but a nibble-at-a-time variant with its own
  initial value. A label carrying `LABELONE`, the `LVM2 001` type string, and a
  zero checksum is detected as nothing at all.
- **mdraid 1.2** was listed by `wipefs` but rejected by `blkid -p` until the
  superblock checksum was added — a folded sum of little-endian words, not a CRC.
  The two tools disagreeing is itself the useful part: `wipefs` enumerates magic
  matches, `blkid` validates.
- **ZFS is deliberately absent.** `libblkid` declares a 64 MiB minimum size for
  its ZFS prober and skips it entirely below that. At 64 MiB, with the uberblock
  magic verified by hexdump at the documented offset in all four labels,
  `blkid -p` still reports nothing. Some further condition is required and **what
  it is has not been established.** The writer is kept, documented, and out of
  the catalogue rather than shipped as a fixture nothing recognizes.

### The question this answered

`ext4-with-stale-mdraid-090-512` exists to settle something two earlier
investigations could not. A 0.90 superblock lives in the last 64 KiB-aligned
block, so formatting the start of a device never removes it, and a device can
carry a current file system and an obsolete array membership at once.

On that fixture, `wipefs -n` reports **both** signatures. `blkid -p -o udev` —
the form udev's builtin uses, and therefore what an unprivileged client reads
from the udev database — reports exactly **one**, and it is the *stale* one:
`ID_FS_TYPE=linux_raid_member`. `ID_FS_AMBIVALENT` does not fire.

So an unprivileged client and a privileged helper can describe the same bytes
differently, and the client's description is the one that is out of date. That is
recorded against Part 5's asymmetry conclusion in `docs/spec-issues/README.md`,
and it is the kind of fact that is cheap to establish with a fixture generator
and expensive to guess wrong in a design round.

## Increment 1c: corrections from the project review

`docs/reviews/PROJECT_REVIEW_2026-07-28.md` found that two of increment 1's
central claims were not true of the code that made them. Both are corrected here,
and both were reproduced before being fixed.

### The interlock's root of trust was a user-writable file

Increment 1 said "disposability is computed, never declared." It was not. The
digest comparison was real, but the *expectations* came from
`tests/generated/MANIFEST` — a plain file in the very directory being verified —
and `Manifest::parse` accepted its token without checking that the token followed
from its own entries. Writing a manifest that named an arbitrary file's digest,
with any well-formed token, authorized that file. This was demonstrated end to
end before the fix.

Two changes close it:

- **Expectations now come from the compiled catalogue** (`catalogue::expected`),
  computed with no I/O. Generation is deterministic, so the expected digests are
  a pure function of the code in the binary. Nothing written to the fixture
  directory can change what the interlock expects — only what is on disk to be
  compared against it. `authorize` no longer accepts a caller-supplied manifest
  at all.
- **Targets are verified by name, length, and digest** against the entry for
  that name. Membership by digest alone was too weak: it admitted any file so
  long as *some* entry anywhere shared its digest.

`Manifest::parse` additionally recomputes the token from the parsed entries and
rejects a mismatch, so a forged manifest is refused wherever it is read, not only
on the interlock path.

This also largely closes the hard-link vector the review raised separately: a
link can now only pass if the file it points at already contains exactly a
fixture's bytes, and destroying that is not a loss. A `nlink > 1` refusal is
added on Unix as defence in depth, because a second name is still a second thing
a destructive suite could reach. Windows exposes link count only through
unstable APIs, so the check is Unix-only and the content requirement carries the
guarantee on both platforms.

### The `Indeterminate` fixture was recoverable, and its test could not tell

`gpt-corrupt-header-512.img` flipped the primary header's CRC and left the backup
header valid and in agreement with the entry array. ADR-C3 defines
`Indeterminate` as a table that cannot be read or parses ambiguously; this one is
positively determinable from its backup. It was a good recovery fixture wearing
the wrong label.

The test that was supposed to catch this asserted only that three *filenames*
existed. It never parsed or classified anything, so it would have passed no
matter what the bytes contained — and the traceability record cited it as
evidence for ADR-C3's three states.

Corrected by:

- renaming the image to `gpt-invalid-primary-valid-backup-512.img`, under an
  honest "damaged primary, intact backup" rationale;
- adding `gpt-conflicting-tables-512.img`, where primary and backup are each
  independently valid and describe **different** partitions, so nothing about the
  table can be positively determined — which is what `Indeterminate` means;
- replacing the filename test with one that **classifies the bytes**, using an
  oracle that recomputes both header checksums independently of the code that
  wrote them.

### Regeneration now prunes withdrawn fixtures

`generate` documented that it replaced the directory contents but only
overwrote current names, so the withdrawn ZFS image survived in working trees. It
now removes files the current catalogue does not produce — but only in a
directory that already holds one of our manifests, so a mistyped root cannot
delete a user's files.

### What the remediation itself got wrong, and an honest note on the token

An independent audit of the review found that the first attempt at the
manifest fix **left a hole its own new tests did not catch.** Containment was
`starts_with(root)` while the name came from `file_name()`, so a byte-identical
copy at `<root>/sub/blank-512.img` satisfied the root check, the name lookup, the
length check, and the digest check simultaneously. It authorized. Verified, then
closed by requiring the resolved path to equal `root.join(name)` exactly — an
equality, not a prefix — with a regression test.

The lesson is the review's own: implementing a recommendation is not the same as
closing the hole it describes, and new green tests around a change prove nothing
about the case nobody thought of.

**The disposable-test token is not a secret.** Since expectations moved to the
compiled catalogue, the token is a pure function of source: identical on every
machine building this commit, computable with no I/O, and printed to stdout by
`cargo xtask fixtures` where CI captures it. Anyone who can read the repository
can derive it.

It proves that the invocation presented the exact build-derived value, and no
more. It cannot prove the operator ran anything: a pure function of public source
can be computed by anyone holding the repository. What it buys is accident
friction — a destructive run cannot be produced by ambient environment state
alone — and SAFE-007's strength here rests on the target verification, which is
computed from bytes and cannot be asserted, not on the token. A factor with
genuinely independent strength would have to be a
per-generation value that is not derivable from source, and that is a decision
increment 2 should make deliberately rather than inherit.

Windows link coverage is also absent: the `nlink` guard is Unix-only because
Rust exposes the Windows link count only through unstable APIs, and adding
`windows-sys` to a crate whose sole dependency is `sha2` is a dependency-policy
decision rather than a code change.

## Increment 1d: a fixture's purpose is computed, not asserted beside it

The review ranked "tests whose names are the safety claim" as the systemic
weakness here, and named the root cause exactly: **no test bound a catalogue
fixture's bytes to its rationale.** Every layout and signature test rebuilt its
own image from its own literals, so nothing connected the catalogue to the
requirements it claimed to serve.

That was reproduced rather than accepted. Two builders were mutated — the LUKS2
fixture reduced to a blank image, and the multi-signature fixture stripped of the
stale mdraid superblock that the Part 5 asymmetry finding rests on — and **all 64
tests passed.** No failure, no warning. The traceability record would have gone
on citing `luks2-whole-disk-512.img` for FS-004 while it held nothing but zeros.

`crates/fixtures/src/evidence.rs` closes it by applying this crate's own rule to
its fixtures. The interlock computes disposability from a target's bytes instead
of accepting an assertion; evidence computes a fixture's *purpose* the same way.
Each catalogue entry has a claim, checked from the bytes its builder produces:

- **Exhaustive in both directions.** A fixture with no claim fails the suite, and
  a claim naming no fixture fails it too. An unregistered name is a refusal, not
  "nothing to check" — the gap would otherwise return one new fixture at a time.
- **Every claim is proved capable of failing.** A check that accepts everything
  would pass a "does it satisfy its claim" test forever, which is the same defect
  one level up. Each fixture is paired with at least one mutation the claim must
  reject, and the pairing is exhaustive. Two of those mutations are the real ones
  above.
- **Generation enforces it.** `generate` verifies before writing, so an image
  that stopped serving its purpose never reaches disk. The refusal names what was
  lost rather than which assertion fired.
- **The oracles are independent of the writers.** A check that called the
  writer's own checksum would prove only self-consistency, so CRC-32 is
  reimplemented by table lookup against the writer's bit loop, LVM2's CRC bitwise
  against its nibble table, and mdraid's sum with an iterative fold. Each is then
  anchored outside this repository: CRC-32 to the published IEEE check value, and
  the other two to `libblkid`, which validates both before naming a format.

### Two documented claims were wrong, in both directions

`corrupt_primary_header_crc` still described itself as producing ADR-C3's
`Indeterminate` state, contradicting `write_conflicting_backup` in the same file,
which had already been corrected. The layout test repeated it. Both now say
*recoverable*, which is what the catalogue has said since increment 1c.

The other correction runs the other way. The response to the project review
recorded that `authorization_cannot_be_forged_outside_this_module` "reportedly
stays green with `verify_target`'s body short-circuited" — read as evidence the
interlock suite was blind to that mutation. **It was run, and it is not.** Ten
tests fail: traversal, subdirectory copies, modified bytes, wrong names, missing
targets, and mixed requests. The named test does stay green, because it asserts a
compile-time property rather than target verification, but nothing about the
suite around it was as weak as the note implied. "Reportedly" was the tell: a
claim recorded without being executed, in a document written about that exact
failure.

### The first version of this fix repeated the defect it was written to end

Increment 1d was put through an adversarial pass — three lenses, each trying to
break a different property — before it was proposed. It found the module
directionally right and its central claims overstated, which is the same failure
this work package keeps recording about itself.

**The gate was proven by nothing.** `generate` refused an image that failed its
claim, and that refusal was load-bearing on nothing: deleting the check kept all
74 tests green, because every test handed `generate` the real catalogue, which
satisfies its claims. Nothing ever exercised the refusal. A safety check no test
can reach is precisely what `evidence` exists to prevent, and it was sitting
inside the fix for it. Closed by splitting out `generate_from`, which takes a
fixture list, so a test can hand it a fixture that keeps a catalogue name and
loses what the name promises. Deleting the gate now fails that test.

**"Anchored outside this repository" was true of one checksum in three.** The
module claimed each reimplementation was anchored externally. For CRC-32 that was
executable — the published check value `0xcbf43926` is asserted. For LVM2's CRC
and mdraid's folded sum there was no pinned value anywhere: changing the initial
constant in *both* the writer and the oracle kept every test green while making
every fixture undetectable. Two implementations agreeing is the "two opinions"
the module's own documentation says is insufficient. Closed by pinning the three
checksum fields to the values `libblkid` 2.41 accepted on 2026-07-28, recorded
with their provenance.

**Ten claims accepted mutations that destroyed the fixture's purpose.** The
checks verified structure the builder always produces and skipped the fields that
carry meaning. The sharpest: `gpt-conflicting-tables-512.img` proved "two tables
that disagree" by comparing entry-array CRCs, and changing one character of a
partition *name* makes the CRCs differ while both copies describe byte-identical
extents — a disk where everything is determinable, still reported as ADR-C3
`Indeterminate`. Others let a partition run 100 MB past a 4 MiB device, let the
4Kn fixture carry the 512-byte arm's literal LBAs, let the ext4 half lose the
feature flags that make it ext4 rather than ext2, and let the LVM2 label declare
a sector it is not in — which `libblkid` skips, and which lies outside the CRC
span, so every checksum stayed valid.

**Two of the mutations proving claims could fail were themselves unsound.** They
tripped a different check than the one under test, so they proved nothing about
it. Every mutation now carries the phrase its refusal must contain, and the
mutations that need a valid checksum repair the one they disturb — otherwise the
checksum check fires first and the claim under test is never reached.

### Two fixture defects the pass found, as opposed to check defects

- **`gpt-missing-backup-512.img` had a backup.** It zeroed the last sector only,
  leaving 16 KiB of byte-identical backup entry array at LBAs 8159 to 8190, which
  any recovery tool that scans rather than seeking to the last LBA would find.
  The fixture now erases the whole backup copy, so it is what its name says.
- **The 512-byte and 4Kn baselines shared a disk GUID**, because both derived it
  from the literal `"gpt-basic"`. Two different media with one identity is a
  manufactured instance of exactly the collision SI-27 is trying to reason about.
  Found by a new catalogue-wide identity check, which no single-image claim could
  have seen, and fixed by labelling the 4Kn image separately. The fixtures
  *derived* from the 512-byte baseline keep its GUID deliberately: they are one
  disk in different states.

### What increment 1d does not close

`catalogue::expected()`, which is the interlock's root of trust, builds its images
with no I/O and deliberately does not call `evidence::verify` — the authorization
path must not acquire new failure modes. So evidence gates what reaches disk, not
what the interlock expects. Every supported path fails loudly first, but the
guarantee is procedural there rather than structural, and increment 2 should close
it when it revisits the token.

Two further findings from the pass are recorded and **not** fixed here:

- **The sandbox directories in these tests are fixed paths under the system temp
  directory**, so two concurrent `cargo test` runs of this crate collide. It has
  not been observed to flake, but the suite is flaky by construction and a
  safety-gate suite is the wrong place for that.
- **Claim substance cannot be checked mechanically.** A fixture can be added with
  a claim that only checks the image's length. What rules it out is the
  requirement that every fixture have a mutation its claim must reject *with a
  named reason* — a check that accepts everything fails that test — but this is a
  process guarantee resting on whoever writes the mutation, not a structural one.

## Carried into increment 2, as preconditions rather than follow-ups

A progress review on 2026-07-28 confirmed these are gates, not refinements.

1. **Bind authorization to the file object, not its name.** Delivered in two
   parts, and the first part was **not** sufficient — recorded here rather than
   smoothed over.

   Increment 2a bound the *post-open* checks to the handle, and the
   2026-07-29 follow-up audit then showed the binding began one step too late.
   `verify_target` resolved the path, then opened it a second time, and an open
   that follows links can leave the fixture tree between those two operations:
   replace `root/name` with a symlink to an out-of-root file holding the
   fixture's exact bytes, and every handle-based check accepts it. Increment 2a
   claimed a raced symlink was harmless because the object is verified after
   opening. That was wrong, and the reason is worth keeping:
   `object_verification_alone_cannot_prove_root_membership` demonstrates that
   the object checks accept an out-of-root file with fixture bytes — they
   establish fixture *shape*, and containment is not a property of content. A
   user's ordinary file may hold those bytes.

   **Increment 2c closes this on Unix. Windows remains open.**

   `Authorization` now holds the fixture directory as an object, and targets are
   opened relative to that handle by catalogue basename — `rustix::fs::openat`
   with `NOFOLLOW`, which needs no `unsafe` anywhere in this crate, so SAFE-009
   requires no exception and no adapter crate for the Unix half. There are no
   intermediate components left for anything to redirect.

   *Corrected 2026-07-30: this paragraph also claimed the directory handle
   "outlives the target handles because `Authorization` owns both". It does not —
   `into_targets(self)` moves the targets out and drops the root field before the
   caller uses them. Nothing depended on the claim, which is why the code needed
   no change when the claim did: containment is established at `openat` time and
   is a property of the returned descriptor, not something the directory handle
   maintains afterwards. The root is still held, for the narrower reason that no
   accessor is offered and a consumer therefore never receives a root path to
   reopen by name.*
   `swapping_the_fixture_root_directory_before_open_cannot_redirect_the_write`
   stages the audit's exact attack through the pre-open seam and compares the
   authorized handle's **inode** against the real fixture's, because the decoy
   holds identical bytes and content cannot tell them apart. Under 2b that
   assertion fails.

   **Increment 2d closes it on Windows too, by a different mechanism, and the
   difference is not cosmetic.**

   Windows still opens the child by pathname, because stable `std` exposes no
   safe handle-relative open. What makes that sound is that no component of the
   pathname can be exchanged while the root is held: the root is opened as a
   directory handle whose share mode excludes `FILE_SHARE_DELETE`, and the
   filesystem then refuses to rename or delete it. So **Unix resolves around
   the attack and Windows refuses it**, and only the first is a property of the
   resolver. The second is a property of *the filesystem driver*, and therefore
   holds exactly as far as the driver does.

   Measured, staging the audit's attack with the handle held: NTFS, `ReFS` and
   the Windows SMB server all refuse the swap. The WSL 9p redirector does not —
   a swap staged from the Linux side succeeded and the subsequent child open
   returned the decoy's object identity. A root that is not locally served is
   therefore **refused outright** rather than trusted, which over-refuses SMB to
   a Windows server, and that is the deliberate direction under SAFE-005.

   Be exact about what the root handle contributes. Ancestor renames, and root
   renames once a target is open, were *already* refused by the target file
   handle before this increment — so a test asserting those would pass with the
   fix removed, and one drafted for this increment did. The root handle closes
   one window: between `RootDirectory::open` and the first `open_child`, when no
   target is open yet. That window is where the whole F-02 attack lives.

   For the record, the history of this precondition — increment 2b closed only
   the final-component form: The second follow-up audit pointed out what `open(2)` documents
   plainly: `O_NOFOLLOW` constrains the *last* path component only, and
   intermediate components are still resolved through symlinks. So the attack
   moves up one level — rename the fixture root `R` aside, put a symlink at `R`
   pointing to an outside directory `E`, place `E/name` with the fixture's exact
   bytes, and `open("R/name", O_NOFOLLOW)` follows the intermediate `R` because
   `name` itself is not a link. The saved strings still satisfy
   `resolved == root.join(name)`, and handle metadata, link count, length and
   digest all pass. A destructive write then lands outside the fixture root.

   This is the same lesson as
   `object_verification_alone_cannot_prove_root_membership`, one directory up:
   matching bytes prove shape, never location. Closing it needs a *held root
   directory object* and a direct-child open relative to it — `openat`-style,
   with the basename from the catalogue — so that path resolution and the open
   stop being two operations with a gap between them. More `canonicalize` calls
   cannot fix it. What increment 2b did deliver:
   `O_NOFOLLOW` on Unix (from `libc`, because the value differs across Linux,
   macOS and the BSDs) and `FILE_FLAG_OPEN_REPARSE_POINT` on Windows, so a link
   at the target's *own* name is refused rather than traversed. A test seam fires between canonicalization
   and open, which makes the race *scheduled* rather than sampled:
   `a_symlink_swapped_in_before_open_is_refused` performs exactly the audit's
   substitution and requires a refusal, and
   `an_object_swapped_in_before_open_is_refused_on_every_platform` covers the
   seam where symlink creation needs a privilege CI cannot guarantee. Removing
   the seam fails those tests by name.

   Residual, and not claimed closed: **the Windows hard-link vector.** A hard
   link is not a reparse point, so no-follow does not refuse one, and the
   `nlink` guard is Unix-only because stable Rust exposes link counts on
   Windows only behind an unstable feature. That is precondition 3 below.

   **At increment 2b's boundary, Tier 2 could not be enabled on a platform until
   the held-root-directory open landed there.** Increments 2c and 2d later
   closed that prerequisite on Unix and locally served Windows volumes; the
   narrower increment-2e Linux acceptance is governed by its own boundary above.

   Also still true of increment 2a, and still the point: [`Authorization`] is
   non-cloneable (a `compile_fail` doctest pins this), consumed by
   `into_targets`, and carries open `File` handles: `fstat`, the hard-link
   count, the length, and every content byte are read **through the handle**,
   and the handle itself — the verified object — is what a destructive
   consumer receives. On Windows the handle's share mode refuses *other*
   openers for as long as the authorization lives — writes to the unnamed
   `$DATA` stream through any name, and rename or delete of the entry the
   handle was opened under. *Corrected 2026-07-30: this used to add "hard links
   included", which read as though the share mode made a pre-existing hard link
   safe. It does not, and F-03 was live because of that reading. Named
   alternate data streams and file attributes are also still writable. Other
   names are refused by counting them, never by the share mode.* On POSIX,
   where no mandatory equivalent exists, the guarantee is that rebinding the
   name cannot change which object is held. The replace-after-authorization test demanded here exists on both
   platform families, and handle-purity is proven *deterministically*:
   `verify_object` takes no usable path, and its test deletes the path before
   verifying, so any check that regressed to a by-path read fails on a missing
   file rather than only during a race. Two regressions were planted to
   confirm the tests catch them (`stat`-by-path for `fstat`, `fs::read` for
   the handle read); both failed by name.

   The by-name `symlink_metadata` check is kept, but only as hygiene that gives
   symlinks their own readable refusal. It is raceable, and after increment 2b
   nothing safety-relevant rests on it.
2. ~~**Decide a genuinely independent token factor.**~~ **Closed 2026-07-29 by
   decision, not by code: [ADR-0007](../adr/0007-safe-007-third-factor.md).**

   The queued answer — "add an entropy source" — was wrong, and finding out why
   is the useful part. `authorize` deliberately trusts nothing inside the
   directory it verifies; expectations come from the compiled catalogue, because
   accepting a caller-supplied manifest was a defect that let a hand-written one
   authorize an arbitrary target. A per-generation random token **cannot** be
   compiled in, so the interlock would have to read it from the fixture root —
   re-creating exactly that trust dependency. An actor who can write the fixture
   root could write the token they intend to present. Randomness would add a
   dependency and a writable-file trust while defeating nobody.

   Read exactly, SAFE-007 requires the three factors to be *present* and forbids
   one environment variable from standing in for all of them. Both hold: the
   profile is a command-line argument, the target is verified from its own bytes
   against compiled expectations through a no-follow open, and the token is the
   only environment variable of the three. It does not require independence, and
   holding the code to a standard the specification does not set is what made
   this precondition unclosable. The token proves only that the invocation
   supplied the exact value derived by this build. It does **not** prove that an
   operator ran the generator, copied its output, or intended the operation;
   public source lets anyone derive it. Its value is accident friction, not
   operator provenance. This is the narrower claim established above and in the
   corrected ADR-0007 decision.

   A real third factor needs state outside both the source tree and the fixture
   root. That is a T2/T3 lab-architecture decision (Section 11.2, increment 3),
   and ADR-0007 records it as the revisit condition rather than guessing at it.
3. ~~**Windows other-name coverage** for the `nlink` guard.~~ **Closed
   2026-07-30 by increment 2d — and it was not a missing check, it was a live
   defect.**

   Reproduced before it was fixed: a file outside the fixture root holding a
   fixture's exact bytes, hard-linked in at that fixture's name. Name, location,
   regular-file status, length and digest all passed, authorization succeeded,
   and a write through the authorized handle destroyed the outside file. The
   link count read 2 through the handle the entire time and was read only under
   `cfg(unix)`.

   The count is now read on both platforms — on Windows through
   `GetFileInformationByHandle`, reached by a safe wrapper. The regression test
   is arranged so that the link count is the *only* check that can refuse it,
   with a control proving the same object authorizes once its outside name is
   gone; the previous in-root test could not discriminate, because there the
   digest disagreed too.

   SI-36 was filed claiming SAFE-009 was ambiguous here and is **withdrawn**:
   SAFE-009 permits `unsafe` *only* in adapter, FFI, and helper crates, which
   forbids it in `crates/fixtures` and names the route in the same clause — a
   narrow platform-query adapter crate with a reviewed module, or a vetted safe
   dependency. The second route is the one taken.

   The audit sharpened what the exposure actually was, and it was right. A
   sentence in `interlock.rs` claimed the Windows share mode closed this hole.
   It does not: `FILE_SHARE_READ` stops *competing* opens, and the write that
   reaches every name is the one this interlock hands over. That sentence is the
   reason the defect shipped, and it is deleted rather than kept as defence in
   depth.

   The toolchain measurement stands. `MetadataExt::number_of_links`,
   `file_index` and `volume_serial_number` are all unstable behind
   `windows_by_handle` (rust-lang/rust#63010), re-verified by compiling against
   the pinned 1.96.0 during this increment, and nightly is a bounded exception
   for `fuzz/` alone. So the check cannot be written with std alone — but "not
   std" is not "FFI", which is where the filed question went wrong.

   The residual that remains is narrower and is stated in
   "What increment 2d does not close" below: the count is a **snapshot** taken
   at authorization, and a new alias afterwards is not prevented.

4. **Bind the loop device to the verified handle before any destructive
   attach.** Filed 2026-08-01 as repository issue #94. The interlock verifies
   a regular file through a held handle, but a loop attach by pathname
   (`losetup <file>`) binds whatever the name resolves to at attach time, and
   nothing asserts the loop device's backing object is the verified one.
   Read-only today the worst outcome is a wrong SI-35 measurement; the moment
   this increment's harness attaches a loop device for a destructive suite,
   the gap is a write to an unverified object. Increment 2e adopts the
   descriptor-bound closure — fd-based `LOOP_CONFIGURE`, `LOOP_GET_STATUS64`
   identity read-back before and after an in-process held-descriptor probe,
   confirmed descriptor-bound detach, and unchanged post-detach fixture hashes
   — for its one read-only acceptance. **Closed 2026-08-03.** The complete
   acceptance, including the adversarial rebind leg, passed on commit `2dbf601`
   in the disposable Proxmox-hosted non-WSL Linux VM; the rebind was detected
   and its observation discarded, detach and partition teardown were confirmed,
   and both fixture digests were unchanged. See "Increment 2e acceptance
   record" above for the run's exclusions and its stated limits. The
   increment-2 row is no longer Blocked, which is **not** the same as
   delivered: no destructive suite exists, so the gap this precondition guarded
   has been closed before — not by — the harness it was guarding.

## The crate-placement decision issue #51 asked for, and why it was not made

Issue #51 framed the open question as *where the `unsafe` FFI lives* —
`crates/adapter-windows/`, which §4.3 already names but §4.2 scopes to storage
adapters, or a new narrow crate, which is a §4.3 deviation needing a record. It
asked whoever picked to record the choice with its reasoning.

**The premise did not survive measurement, so the choice is not between those
two.** Both halves are reachable without `unsafe` anywhere in this repository:

- Containment needs a *held directory handle*, not a handle-relative open.
  `std::fs::OpenOptions` with `FILE_FLAG_BACKUP_SEMANTICS` opens a directory,
  and `share_mode` is already stable — the same extension trait this file has
  used since increment 2b.
- The link count needs `GetFileInformationByHandle`, which `winapi-util`
  exposes safely.

Recorded because a rejected option is worth as much as a chosen one:

- **FFI in `crates/adapter-windows/`** — rejected on scope. That crate's remit
  is translating canonical storage operations to native APIs. Populating a
  spec-named crate with test-interlock file-identity queries widens both its
  purpose and its reviewers' obligations, permanently, before its real work
  exists.
- **FFI in a new narrow crate** — rejected, but **not on specification
  grounds**, and issue #51 overstated its cost. SAFE-009 permits `unsafe` in
  FFI crates, so a crate that is nothing but FFI sits *inside* the permission
  rather than as an exception to it, and §4.3 is a *proposed* layout that
  `crates/fixtures` and `crates/tokens` already sit outside. The real cost is
  process: a `Governance:` pull request for the owned path, a sub-file grant
  against WP-000's root `Cargo.toml` for the member entry, and an explicit
  opt-out of the workspace lint. **That is a process argument, not a safety
  one, and must not be read as one.** It stays the fallback if the
  single-call-site confinement cannot be held, or if the 128-bit
  `FILE_ID_INFO` is ever needed.
- **`NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory`** — the true `openat`
  analogue, and the only route that would also have survived the 9p case,
  because it would make Windows containment a property of resolution rather
  than of refusal. Rejected for now: it is ntdll rather than kernel32, it was
  not measured, and it is unnecessary while non-local roots are refused
  outright and Tier 2 stays unavailable on Windows. **Revisit it if Tier 2 is
  ever enabled on Windows.**
- **The `rustix` analogy as justification for the dependency** — rejected as an
  argument, though the dependency stands on its own. `rustix` takes
  `BorrowedFd<'_>` and is I/O-safe by construction; `winapi-util` predates Rust
  I/O safety and hands out an unlifetimed `HandleRef` from safe code. During
  review, a use-after-close returning another file's identity was compiled
  inside a crate with `unsafe_code = "deny"` and no `unsafe` token in it. That
  asymmetry is why the wrapper is reached through exactly one function and why
  a test counts the call sites.

## What increment 2d does not close

Stated here so none of it can later be read as closed.

- **Non-Microsoft filesystem providers.** UNC and verbatim-UNC roots are
  refused, which catches `\\wsl.localhost\…` and `\\server\share\…`. It does
  **not** catch WinFsp, Dokan, sshfs-win or a mapped drive that canonicalizes to
  a *drive letter* — those are indistinguishable from a local volume by a
  path-prefix check. Separating them needs a volume-class query no safe wrapper
  here exposes. **Containment on Windows is unproven for any root not on a
  local volume.**
- **Samba, NFS, FAT32 and exFAT** were not constructible on the measuring host.
  Samba has defaulted to `kernel share modes = no` since 4.9, which is the same
  failure class as the reproduced 9p break. Reasoned, not measured.
- **New hard links after authorization are not prevented**, on either platform.
  The count is a snapshot; `a_new_hard_link_after_authorization_is_not_prevented`
  exists to keep that from being upgraded into a guarantee by prose. Why it is
  tolerable is an *argument*, not a measurement of impossibility: the bound
  object cannot be renamed or deleted under its own name while the handle
  lives, and its bytes were verified, so an alias created in that window names
  content already established as disposable. Attack the argument, not the word
  "snapshot".
- **Alternate data streams and file attributes** can still be written on the
  verified object while the authorization is held. Neither destroys user data
  through this handle, and both falsify any unqualified "the share mode refuses
  concurrent writes".
- **The 8.3 short name is an uncounted second directory entry** on 8.3-enabled
  NTFS. It cannot leave its parent directory, so it is not a route out of the
  root — but "reachable under exactly one name" would be false, which is why
  the refusal now says "hard links".
- **`ReFS` file identity is evidenced, not proved.**
  `BY_HANDLE_FILE_INFORMATION`'s 64-bit index is documented as not guaranteed
  unique on `ReFS`, and this repository's own working copy sits on a `ReFS`
  volume. The suite was run with its root there and passed 36/36, and no
  collision was produced. The 128-bit `FILE_ID_INFO` that would settle it is
  not exposed by the safe wrapper, so this stays "measured to hold here"
  rather than "cannot collide".
- **The reparse-point path has no CI-portable test.** A file symlink needs
  `SeCreateSymbolicLinkPrivilege` or Developer Mode, so
  `a_file_symlink_swapped_in_before_open_is_refused_as_an_irregular_object`
  prints a visible skip where neither is present, and on such a host the
  handle-based `is_file()` guard is unprotected against removal.
- **Test and production volumes differ, and the override has been used.**
  Sandboxes are built under `%TEMP%` unless `PARTMAN_TEST_ROOT` says otherwise,
  while real fixtures go to the clone. On the measuring host those are different
  filesystems — NTFS and `ReFS` — so a default run is evidence about `%TEMP%`
  only. The suite has been run against the `ReFS` volume and passes; **CI has
  not**, and adding a second Windows job for it is worth considering. Doing it
  found a real defect: a `PARTMAN_TEST_ROOT` containing forward slashes made
  `mklink` treat a path segment as a switch, junction creation failed, and the
  root-swap control blamed the platform. The separators are now normalised and
  the message names the likely cause. Neither the containment nor the
  other-name property was affected — but a control that fails for the wrong
  reason is exactly how a real failure gets waved through.
- **A third party can deny the root open**, which now fails closed with its own
  refusal rather than being reported as an unreadable manifest. There is
  deliberately no retry: retrying a safety precondition until it passes turns a
  gate into advice.

## Increment 1e: the last manual check, automated

The project review left one finding open here: **"real-prober acceptance is
manual, not regression-protected."** It was the last place in this package where
an important property rested on a person having looked once. Someone ran `blkid`,
read the output, and wrote a table into a document — and nothing re-read it.

That matters because increment 1d's evidence layer proves a fixture's *structure*
is what its rationale claims, which is necessary and not sufficient. A structure
this project believes is correct can still be one `libblkid` declines to name,
and two of the signature writers here were exactly that until their checksums
were reproduced. Neither the format documentation nor this crate's own tests
could have said so.

`cargo xtask probe` re-runs `blkid -p -o udev` and `wipefs -n` over every
generated fixture and compares against `crates/fixtures/src/prober.rs`. Both
tools are read-only and are handed regular files, never a device, so the check
stays unprivileged. It needs Linux, so CI runs it as its own job rather than
inside `cargo xtask ci`.

**The comparison is a chosen subset, deliberately.** `blkid` emits keys that vary
by version, and the fixtures are probed on at least two — 2.41 in development and
whatever `ubuntu-24.04` ships. Comparing the whole output would fail on a
toolchain upgrade rather than on a fixture regression, and a check that fails for
the wrong reason gets disabled rather than fixed. So it is exact over the format
name, identity, label, partition-table kind, and the **full set** of `wipefs`
signature offsets — compared in both directions, because a fixture quietly
gaining a signature is as much a regression as losing one — and silent about the
rest.

**The table is checked on machines with no prober too.** A verbatim capture of
the real 2.41 output is embedded in the tests, and the recorded expectations are
compared against it. Without that, the table would be a hand-written list only a
Linux CI job ever tested, and a transcription slip between the measurement and
the table would look exactly like a passing test. The comparison is also proved
capable of failing in all four directions: a format no longer detected, a changed
answer, a lost signature, and an added one.

### What the automation pinned down

Three rows are not what a reader would predict from the fixture's name, and each
now carries the reason so nobody "fixes" the fixture:

- `gpt-basic-4kn.img` reports **`PMBR`, not `gpt`** — file-based probing assumes
  512-byte sectors, so the 4Kn table at `0x1000` is never read. IMG-011 evidence
  cannot come from file probing at all; it needs a loop device with an explicit
  sector size, which is Tier 2.
- `gpt-conflicting-tables-512.img` is **byte-identical to `gpt-basic-512.img`**
  from both tools. That equality is SI-35, and it is now asserted rather than
  observed once: if `libblkid` ever separates them, the test fails and SI-35
  narrows.
- `ext4-with-stale-mdraid-090-512.img` reports the **stale** membership as its
  single answer while `wipefs` enumerates both. Part 5's asymmetry conclusion and
  SI-34 both rest on that, and it is now a test rather than a paragraph.

### Its first run falsified a claim increment 1 had recorded

The check earned its keep immediately, which is the strongest argument for having
built it. On `ubuntu-24.04` — util-linux **2.39.3** — `blkid -p` reports
**nothing** for `mdraid-1.2-member-512.img`, while `wipefs` still lists the
superblock at `0x1000` and both tools agree about every other fixture, including
the 0.90 superblock in the stale-pair image.

Increment 1 verified the signature writers by hand against `libblkid` 2.41 on one
machine and recorded the result as unconditional. It is not: **FS-004 Linux RAID
and LIN-005 are not established on the util-linux a stock Ubuntu 24.04 ships.**
A manual check on one machine cannot find that, and a table nothing re-reads
cannot report it.

The expectation is now version-keyed rather than relaxed. Below 2.41 the recorded
answer is *silence*, so a prober that starts naming the fixture fails just as one
that stops does, and the `wipefs` enumeration is still required on both. Neither
version's behaviour can drift unnoticed.

**The cause is unestablished and is recorded as such.** Both versions' checksum
routines are arithmetically identical, and the fixture satisfies the magic,
`major_version` and `super_offset` checks 2.39 documents. Finding the failing
condition needs a 2.39 environment to bisect against, which this project does not
have. `docs/quality/observability.md` records what was ruled out, in the same
posture as the ZFS writer: the negative result is kept so it is not rediscovered,
and no mechanism is asserted without measuring it.

### What increment 1e does not close

`libblkid` is one prober. macOS and Windows have their own, this establishes
nothing about either, and the `docs/quality/observability.md` gaps for those
platforms are unchanged. BitLocker, Storage Spaces, LDM and a recognized ZFS
member still have no fixtures, so the FS-004 rows they would occupy are absent
from the table rather than failing in it — an expectation cannot regress for a
fixture that does not exist.

## Increment 1f: the fail-open edges, including one increment 1e introduced

A progress review found two fail-open paths and one flaky-by-construction test
harness. The first is the sharpest, because it is a defect increment 1e created
in the module increment 1d wrote about.

**The prober parsers discarded what they could not read.** `parse_wipefs` used
`filter_map` and `parse_udev` silently dropped any line without `=`, so a row a
parser could not read was **not** an "unexpected signature" that `compare` would
report — it was *no observation at all*. On `blank-512.img`, whose expectation is
nothing, an entirely changed output shape parsed as empty and passed. Meanwhile
the module's own documentation claimed the signature set was "compared in **both**
directions". Increment 1d exists to end claims that outrun their code, and this
one was written one increment later, in the module documenting that rule.

The test beside it, `the_parsers_read_the_shapes_the_tools_actually_emit`, fed
the parsers only valid output. Increment 1d had just established that every claim
needs a case proving it can fail; that rule was not applied one module over.

Both parsers now return `Result` and refuse a line with no `=`, an empty or
repeated key, a non-hexadecimal or unprefixed offset, a row naming no type, a
header anywhere but the first line, and a repeated row. `probe_output` no longer
uses `from_utf8_lossy`, because substituting U+FFFD hands the parser a line the
tool did not emit. Genuinely empty output is now the only route to an empty
observation.

**Directory ownership was inferred from a filename.** Pruning was guarded by
`root.join(MANIFEST_FILE).is_file()`, which establishes nothing about who wrote
the file and follows a symlink besides. Any directory holding an unrelated
regular file — or a link — named `MANIFEST` was treated as ours and could lose
its other regular files. The regression test covered only a directory with *no*
manifest, so it proved less than its name said.

Ownership is now computed, the same rule the interlock applies to a destructive
target: a regular file reached without following a link, whose contents parse as
one of our manifests, with `Manifest::parse` recomputing the token from the
entries so a hand-written file cannot claim ownership either. Every failure is a
refusal to prune.

**The sandboxes were flaky by construction.** Catalogue and interlock tests used
fixed paths and deleted them at setup and drop, so two concurrent `cargo test`
runs of this crate erased each other's fixture trees — in the suite that gates
destructive execution. Each directory now carries the process id and a
per-process counter.

Each of the three fixes was verified by reverting it and confirming the new tests
fail: the old ownership guard fails
`a_foreign_file_named_manifest_does_not_authorize_deletion`, and a `filter_map`
parser fails both `a_line_the_parser_cannot_read_is_refused_rather_than_dropped`
and `a_changed_output_shape_cannot_pass_as_a_blank_fixture`.
