## 1. The question, and the walls around it

SI-11 asks for the protection construction: the closure that decides
which nodes Section 2.1 reaches, total fail-closed verdicts, downward
reach without sibling capture, device-scope inheritance, per-operation
status, step-level construction and decode checks, and exhaustive
PART-014 classification. The walls, each recorded before this round:

- **Round one** fell on status mapping: `unsupported` where MAC-009
  requires `blocked`. The three-regime mapping that survived round
  three keeps MAC-009 intact and is retained here.
- **Round two** fell on sibling capture (protection flowing from a ZFS
  member up through the device and back down into the ESP) and on the
  SI-27 naming gap. The three-edge-kind taxonomy that fixes the
  category error is retained.
- **Round three** fell on six defects: no downward production rule
  (the root-on-ZFS-over-LUKS case — deleting the partition reaches the
  encryption layer and never sees the pool below), a fail-open
  residual arm, re-derived sibling capture through
  parent-of-created-node, device-scope refusals unreachable from
  below, a missing CAP-002 operation dimension, and a constructor that
  collapsed to the runtime-guard axis. Every one has a named
  counter-mechanism below.
- **Fail-closed-by-unencodability is not fail-closed** (Part 6's
  governing finding): every refusal in this design is a typed,
  encodable artifact. No collision, residual, or refusal surfaces as
  an encoder error.
- **ADR-0016's contract obligation**: the verdict binds to a named,
  deterministic helper evidence contract with measured re-probe
  stability. An unnamed evidence set is round two's refuted premise
  returned.
- The round-four preconditions are discharged at the width this round
  needs: all three platforms have non-elevated observability records;
  the Linux designator rows exist (L7), with the Windows
  Storage-Spaces/LDM designators recorded as display-and-naming
  inputs rather than verdict inputs under the architecture below.

What changed the design space since round three: **the verdict is now
helper-authored body content (ADR-0016) and table state is
helper-parsed from raw sectors (ADR-0014).** The client still runs the
same closure over its draft snapshot — that is ADR-0012's construction
layer — but the authoritative computation is the helper's, at
validation, over its own re-discovery. Client-invisible protecting
facts (measured: M7's byte-identical-to-blank projection, L4/L10's
stale-single-answer cache) are therefore inside the operative layer's
view, and the closure can be designed against the helper's evidence
without pretending the client sees it.

## 2. Recommendation

Twelve clauses. Together they answer Part 6's eleven items; the
mapping is given at each clause.

### 2.1 The verdict: three-valued, total, inverted default *(items 2, 7)*

Per node: `Permitted` | `Refused { class, reason }` |
`Indeterminate { cause, remediation }`. The function is **total by an
enumerated match with an `Indeterminate` residual arm** — never
`Permitted`. Enumerated arms exist for: an indeterminate partition
table (ADR-0014's parser output), an unrecognized file system or
signature (SAFE-005's first clause, honored rather than wildcarded),
a locked encryption layer (2.9), an orphan signature (2.9), an
unrecognized transport (2.5), and every `Unrecognized` enum variant
ADR-C5 mandates. A property test generates nodes across every kind
including unrecognized variants and asserts the residual is never
`Permitted`.

Placement is decided, not re-argued: the verdict is hashed-body
content, helper-authored at validation (ADR-0016 discharges Part 6
item 7). Verdict inputs are restricted to facts that satisfy
MODEL-005's body-stability rule; mount state, active swap, health,
and tool availability feed Regimes B and C (2.8) — reasons and
runtime gates — never the verdict.

### 2.2 The evidence contract, named *(ADR-0016's hard input)*

The verdict binds to a two-layer contract, per platform:

**The byte layer: the helper's own bounded parsers over raw device
bytes.** ADR-0014's architecture generalized from the table to every
on-disk verdict input. `crates/table-parser` already exists; the
signature-family parsers join it — ZFS vdev labels (all four
positions, both end pairs), mdraid 0.90 and 1.x superblocks, LUKS1/2
headers, LVM2 label and metadata area, Storage Spaces and LDM
markers, APFS container superblock (member count and UUID), BitLocker
metadata, and the file-system superblocks FS-004 lists. Each parser
is bounded, `unsafe`-free, Section 11.4 fuzz-obligated, and fixed by
family, offsets, magic, and checksum validation. **The layer is
enumerating by construction: every family is probed at every defined
location and every validated match is reported.** Nothing is
priority-resolved, so the measured intra-helper asymmetry — `wipefs`
enumerates both signatures of the stale pair where root `blkid -p`
reports exactly the stale one (L5, L10) — is dissolved the way
ADR-0014 dissolved the table-state one: the contract is the product's
own parser, not "run a privileged tool," and there is no precedence
question because nothing is discarded.

**The state layer: named platform APIs for facts that are not on
disk.** Transport/bus class, multipath assembly and membership, NVMe
subsystem/shared-namespace capability, device read-only state,
removability. Named per platform: Linux — sysfs attributes and the
device-mapper/holders topology by path; Windows — Storage Management
API classes (`MSFT_Disk`, `MSFT_PhysicalDisk.BusType`, the
Storage Spaces pool-membership class measured readable in Part 5);
macOS — named IOKit registry keys (never `system_profiler` output,
per Section 16). Each fact carries ADR-C4's outcome vocabulary; an
`unavailable` or `failed` state-layer fact makes the consuming arm
`Indeterminate`.

**The join rule — the only cross-layer precedence, stated once:**
the join is protective. Evidence of a protected technology from
either layer suffices for its refusing arm; `Permitted` requires
every arm input either positively determined in its layer or
positively absent; a positive disagreement between layers is
`Indeterminate`. The join is monotone over a finite input set, so
the contract is deterministic given its inputs.

**Stability, at honest scope.** The byte layer is a pure function of
device bytes; its re-probe stability is byte stability, measured
where it has been measured (digest-bracketed double captures: L3, L5,
L10; M10's double-read) and inherited from the fixture discipline
elsewhere. The state layer's double-capture stability is **partially
measured** (L3's kernel view; the Windows sittings' property
retention) and the remainder is a named evidence obligation of the
resolution (§5), owed before any arm consuming an unmeasured
state-layer fact leaves `Indeterminate`. A verdict change on a true
state change is not instability — it is ADR-0016's divergence rule
doing its job and rejecting the plan.

### 2.3 The effect table and the affected-set closure *(items 1, 3)*

Round three's open parameter — which effect classes count as
substrate destruction — closes by enumeration. **Every CAP-002
mutating operation maps normatively to three range sets** on
host-qualified extents (2.11): *written table extents* (the exact
primary/backup GPT, MBR sector, and EBR extents of the host's table
node — never the parent device), *consumed free ranges* (which the
constructor verifies intersect no existing node's extent, the 11.2
overlap invariant enforced at construction), and *destroyed ranges* —
where **release is destruction**: a range freed from its owner (a
deleted partition's extent, a shrink's truncated tail, a move's
source extent at commit) is destroyed even though no byte is
overwritten, because its content ceases to be referenced.
Relocation classes (move, copy-then-commit) exempt the relocated
target's own subtree from destruction descent — its content is
preserved by contract (PART-005) — and MUST either preserve hosted
signatures byte-wise or enumerate their loss explicitly in the plan.

**The affected set is a fixpoint over those ranges:**

1. Seed: the target node; the written table extents; the consumed
   ranges.
2. **Downward containment, range-bounded:** every node whose
   host-qualified extent intersects a destroyed range joins the set.
3. **Upward backing:** a `BackingSignature` in the set brings its
   consumer (the aggregate or encryption layer it evidences).
4. **Downward production, restricted to destroyed substrate:** a
   producer node in the set through a destroyed range brings its
   products — the mapper device an encryption layer produces, the
   virtual devices and volumes an aggregate produces — and the
   descent recurses over the products' own hosted content.

A mutating step **constructs only if every node in its affected set
is `Permitted`** (or carries a valid acknowledgment under 2.9).
`Refused` in the set makes the step unrepresentable — ADR-0012's
axis, discharged at the constructor (2.10). `Indeterminate` in the
set refuses construction with a typed artifact carrying the cause
and remediation — fail-closed with something to display, journal,
and act on, per Part 6's governing finding.

This is round three's missing downward rule, built in: deleting
`sdb1` on root-on-ZFS-over-LUKS destroys `sdb1`'s range → the LUKS
signature and layer are in the range → production brings the mapper
device → its hosted ZFS member signature → backing brings the pool →
`Refused`. `vgremove` on a VG holding a ZFS-backed LV and
`mdadm --zero-superblock` on an array carrying a pool close the same
way: the aggregate's destruction brings its products and their
content.

### 2.4 The non-interference theorem, re-proved as a property *(items 1, 3)*

**Claim:** a step's affected set contains no node whose extent is
disjoint from the step's destroyed, consumed, and table ranges,
unless reached through backing or production from a node inside
them. The premise it rests on, stated as a named property of the
edge taxonomy: **no backing or production edge targets a physical
device** — products are virtual devices, volumes, or file systems;
containment descent is strictly range-bounded; and table writes
target table extents, not the parent device.

Consequences, each a committed regression on the named layouts:

- `zpool create tank /dev/sda2`, then create a BIOS boot partition
  on `sda`: affected = table extents + consumed free range → the
  pool member at `sda2` is untouched → **constructs**. Initialize
  `sda`: destroys `[0, len)` ⊇ `sda2` → pool → **refused**. (Item
  3's required regression pair.)
- The ESP at `sda1` is never captured by its sibling's pool:
  containment descent is range-bounded and the ESP hosts no edge
  from the destroyed range. Fusion `disk0s2` does not freeze
  `disk0s1` for the same reason. (Round two's failure, categorical.)
- `lvresize lv_home` writes the VG metadata area and destroys
  `lv_home`'s own tail in `lv_home`'s address space; `lv_root` is
  not a producer's product of anything destroyed → unreached.
  Btrfs `device delete (sdc1)`: a file system is not a producer;
  closure stops at the file system → `sdb1` unreached. (Round
  three's hand-checked candidates, now property-tested.)

**The theorem is proved as a property test beside the inverted-
default test, not asserted.** The premise is quantified over edge
kinds, so SI-27's round inherits a stated obligation: any edge kind
it adds (the multipath membership edge ADR-0011 deferred to it, the
host-backed-virtual-device edge its round-three record requires)
must either preserve the premise or re-prove the theorem under the
new edge set before acceptance. This design does not depend on the
names SI-27 chooses — only on that property.

### 2.5 Device scope: the transport arm inverted, and SI-37's home *(items 1, 2; SI-37)*

Round three's transport enum listed three network transports while
Section 2.1 says "etc.", leaving NVMe-over-TCP fully mutable. The
default inverts: **the device-scope transport arm carries a closed
positive list of local transports** — NVMe over PCIe, SATA, directly
attached SAS, USB mass storage, SD/MMC, and the paravirtualized
local classes — and everything else, including every unrecognized
transport, is `Indeterminate` at device scope (`blocked`, with the
network-block-device non-goal cited where the class is recognized as
remote: `Refused`).

**SI-37's fail-closed home.** The uncovered population — two
simultaneous paths to one LUN, no platform-assembled node, unequal
identifiers — is covered by construction for every non-local
transport (refused or blocked above, regardless of identifiers). For
the positive-local population, the design adds **per-transport
path-multiplicity contracts** in the state layer: NVMe — the
namespace's own shared-capability report (CMIC/NMIC) and the
platform's subsystem grouping; SAS/SCSI — the device-reported WWN,
whose cross-path equality fires ADR-0011's existing SAFE-005
ambiguity rule; SATA, USB, SD — point-to-point by transport
construction, recorded as such. Where the contract's answer is
`unavailable`, or reports multi-path capability without a
platform-assembled node, mutation is `blocked`. A single-controller
NVMe namespace reporting no shared capability is positively
single-path by the device's own report and is `Permitted` at this
arm — which keeps ordinary machines working while the unmeasured
population fails closed.

**SI-37 is not resolved by this.** Its evidence clause requires the
dual-path matrix and negative controls before any option is
accepted, and no such measurement exists. What this design does is
what the filing asked of SI-11: names the case explicitly and gives
it a fail-closed rule whose predicate is observable. The
recommendation for the register: SI-37 stays open, **stops gating
increment 3** (its population is typed and blocked, so the type is
writable), and its matrix becomes the acceptance evidence for any
future arm that would move that population to `Permitted` — the
SI-28-floor pattern applied to multipath.

### 2.6 Node-local inheritance for device-scope refusals *(item 4)*

A node's effective verdict is the worst of its own arm and **its own
root device's** device-scope verdict. This is a node-local rule, not
a closure rule: a partition inherits only its own device's transport
refusal, read-only state, or whole-device ambiguity, so
`mkfs.ext4 /dev/sdb1` on an iSCSI LUN is refused through inheritance
while an ESP on a SATA disk carrying a ZFS member is not — the
refusal it would wrongly inherit lives on the sibling's backing
signature, not on the device. Inheritance cannot re-derive sibling
capture because it never traverses an edge.

### 2.7 Per-operation status: regimes, operation classes, and the canonical step *(items 5; round one's wall)*

The regime mapping survives from round three, with the two repairs
its review demanded:

- **Regime A** — `Refused { NonGoal }`: mutating operations report
  `unsupported`, reason citing the exact Section 2.1 clause and
  technology.
- **Regime A′** — SAFE-005 ambiguity and every `Indeterminate`:
  mutating operations report `blocked` with the cause and a
  remediation. Ambiguous identity routes here, never to A — the
  reason names SAFE-005, not a technology it cannot identify.
- **Regime B** — PART-014 protected objects: **status unchanged**,
  reason and confirmation strength attached (2.8). MAC-009's
  Recovery-only rule stays intact: those operations are Regime C
  `blocked` with that exact reason.
- **Regime C** — runtime preconditions (missing tool, version, lock,
  dirty volume, Recovery-only, pool health): `blocked`.

**The operation-class dimension** (round three's defect 5): CAP-002
operations partition into mutating classes and source classes
(`detect`, `read`, `check` in read-only mode, `copy`-as-source). A
refused or indeterminate verdict suppresses only the mutating
classes. Source classes are never suppressed by verdict — WIN-004's
copy-off-LDM stays advertised, `detect` on a Storage Spaces pool
stays `supported` per WIN-003 — under the **source-access
predicate**: a refused or indeterminate node may be an operand only
of steps that are source steps in their entirety, with the read-only
invocation mode helper-verified (FS-005's health check on a dirty
NTFS inside an LDM partition runs read-only or not at all).

**CAP-005 agreement by construction** (the attack in §3 that forced
this clause): the capability engine computes a mutating operation's
status from the **canonical step** for that operation on that target
— each CAP-002 operation defines its canonical effect-table entry
over the target — and runs the same closure the constructor runs. One
computation, two callers; the planner and the capability engine
cannot disagree on a target/operation pair.

### 2.8 PART-014, exhaustively classified, outside the body *(item 11)*

The class function is written out in the ADR over all nine
enumerated kinds, per platform, from helper-side live discovery:

| PART-014 object | Discriminant, per the contract |
| --- | --- |
| EFI System | partition type GUID (byte layer) |
| Microsoft Reserved | partition type GUID (byte layer) |
| Windows Recovery | partition type GUID + BCD/ReAgent references (state layer) |
| Apple recovery | APFS volume role (byte layer / IOKit) |
| Apple sealed system volume | APFS role + seal state (IOKit) |
| Signed system snapshots | the flag ADR-C5 placed on the carrying file system |
| Linux boot | mount path `/boot`, `/boot/efi` (state layer), plus fstab-declared purpose where readable (LIN-010's read) — Debian's generic-GUID `/boot` is identified by mount, not GUID |
| Active swap | `/proc/swaps` / platform equivalent (state layer) |
| Current boot/root volumes | mount table root + EFI boot entries (state layer) |

Regime B never enters a verdict, so none of this is body content —
which is also what keeps mounts and swap state out of the hashed
body, consistent with MODEL-005's body-stability rule. The class
attaches reasons and confirmation strength (PART-003's safeguards,
UI-009's typed confirmation). **The bounded miss is named:** an
unmounted, fstab-invisible generic-GUID `/boot` is unidentifiable;
because Regime B never flips status, the miss costs a warning, never
a safety property.

### 2.9 Acknowledgment-gated arms: the escape that is not a bypass *(item 2; round three's orphan and locked-layer rejections)*

Three arms sit between `Permitted` and `Refused`, and their shape is
the round's answer to "blocked forever" without reopening PART-014's
bypassable gloss:

- **Orphan and released signatures.** A validated signature whose
  consumer is not observed — the exported ZFS label (its own state
  field parsed by the byte layer), the stale mdraid superblock in a
  shrink's released tail, the unassembled member — is
  `Indeterminate`: `blocked`, remediation "import/assemble to
  confirm, or record the release acknowledgment." The
  acknowledgment is a typed, hash-bound plan value naming the
  technology, the parsed designator, and the consequence ("this
  disk carries an exported ZFS label for pool GUID X; destroying it
  makes that pool unimportable"), recorded at plan creation under
  UI-009 typed confirmation. With it, the step constructs.
- **A consumed member has no acknowledgment.** Where the consumer
  *is* observed — the pool imported, the array assembled, the space
  online, or the label's own state field saying active — the arm is
  `Refused` and **its constructor has no acknowledgment parameter**.
  The distinction from PART-014's "without an explicit supported
  plan" is representational, per ADR-0012: the bypass the register
  condemned was a guard any plan could talk past; this is a type
  with no sentence for the consumed case, and the helper re-derives
  the arm at validation — an acknowledgment authored against an
  orphan that validation finds consumed is a divergence and rejects.
- **Locked encryption layers.** A locked layer's contents are
  unenumerable by anyone, helper included. Destructive operations on
  it are `Indeterminate`: `blocked`, remediation "unlock, or record
  the opaque-destruction acknowledgment" — FS-010's recovery-material
  acknowledgment plus a typed statement that the container's
  contents cannot be verified. Round three's defect (a locked
  container holding a pool destroyed at `supported`) is closed: the
  destruction is never silent, never default, and never `supported`
  without the recorded acknowledgment.
- **Indeterminate tables.** Against an `Indeterminate` table state,
  exactly one write family is permitted: **restore from the
  product's own identity-bound table backup** (PART-013's artifact,
  REC-001's validation). Free-form table writes are `blocked`, and
  PART-001 initialization stays governed by its categorical
  invariant — a fresh, positively determined `Absent`, which an
  `Indeterminate` table never satisfies. (Item 2's "settle it in
  the ADR, not in an adapter.")

### 2.10 The constructor, the decode check, and the single engine *(item 6)*

The only way to obtain a mutating `PlanStep` is a constructor that
takes the snapshot body, the target, the effect-table entry, and the
structural effects; computes the affected set and verdicts; and
returns either the step — carrying its affected set and the
host-qualified estimated ranges Section 6 requires — or a typed
refusal. There is no other constructor; the compile-fail proof lands
in the pattern ADR-0012 names.

**Decode re-runs the closure.** The schema-validation pass — the
named sole decode boundary, with its own error type — recomputes
affected sets and verdicts from the decoded snapshot and steps and
rejects any plan whose recorded sets disagree with recomputation,
mutation-verified. A hand-forged artifact fails at every decoder
before it fails at the helper, and fails at the helper regardless
(HLP-002).

**The TypeScript cost, argued rather than assumed** (item 6's
demand): the closure is implemented once, in the Rust engine.
TypeScript carries what MODEL-005 actually requires of it — byte-
identical canonical encoding and hashing, already proven by golden
tests — plus structural schema validation. The GUI does not
recompute verdicts in TypeScript: CAP-005/CLI-003 already require
every surface to be served by the one engine, the desktop shell
reaches the Rust core in-process, and CAP-007 makes client-shown
capability advisory. The alternative Part 6 priced — dropping the
affected set from the body and re-deriving it helper-side — is
rejected on ADR-0016's ground: the affected ranges are what the
user authorizes (UI-005 shows them; consequence text derives from
them), and un-authenticating them re-opens the divergence class the
verdict's body residence just closed.

### 2.11 Bind set, extent accessor, free extents *(items 8, 9)*

**The bind set** (CONC-001) is the transitive closure of the
affected set under reverse backing, reverse production, and
**ancestor containment**, down to and including every device node —
shrinking `sda1` binds `sda`, so two plans cannot rewrite one GPT
concurrently (round three's lost-update path closed). The rule is
stated over edge semantics, not edge names: every edge kind whose
meaning is "the bytes of A live within or derive from B" is
traversed in reverse. When SI-27 lands the host-backed-virtual-
device edge, a loop device's bind set reaches through its backing
file to the physical device by the same rule with no restatement —
and until both SI-27 and this issue resolve, nothing constructs, so
the currently-empty loop bind set cannot be exercised. The
dependency is stated, not solved around.

**The extent accessor is total by domain restriction**: extents
exist on the extent-bearing kinds (device, table — with explicit
primary/backup/MBR/EBR extents — partition, signature with its
primary offset, file system with its superblock offset); the extent
clause is vacuous elsewhere by stated rule, not by panic. Every
range is host-qualified; one address space per containment-forest
root, so an MBR logical's offset has exactly one meaning and a
produced virtual device roots its own space.

**Free extents leave the hashed body.** They carry no verdict input;
PART-009/PART-012 compute placement from the planner's own policy;
and keeping them would force the GPT reserved-region, minimum-gap,
and alignment rules into the canonical schema for no authenticated
consumer. The constructor's consumed-range check works on ranges,
not on `FreeExtent` nodes. (Item 9's either/or, taken on the cheap
side.)

### 2.12 Rulesets, RecoveryRequired, and the update route *(item 10)*

The closure and arms are versioned and ship compiled into the helper
(SAFE-008). **No plan is ever evaluated under the ruleset it
declares** — HLP-002, CAP-007, and SAFE-008 already forbid it; the
prohibition is restated at the constructor and the validator with a
negative test, which is where round three found the implementation
pressure. A ruleset change that alters any verdict within a bound
target set is, by ADR-0016's standing rule, a divergence: it rejects
before the first write, invalidates Draft/Validated plans per
CONC-003, and on resume-after-update the plan passes through
`Revalidating` under the new rules — a changed verdict strands into
`RecoveryRequired` with its recovery actions **re-planned under the
current ruleset** (Section 8's "recovery actions are themselves
plans"), and REC-010 stops advertising a rollback whose reversal
plan no longer validates. The stranded-machine cost is intrinsic to
authenticated verdicts, as Part 6 recorded; this clause routes it
fail-closed and defers the retention/lifecycle machinery to SI-20
through SI-22, whose register rows gain nothing and lose nothing
here.

### 2.13 SI-29: Storage Spaces content, the narrow reading with a geometry line

**Recommendation: the protected objects are the pool, the spaces as
structural objects, and the member-disk substrates — not the file
systems inside a space.** An NTFS resize *within* a space's existing
provisioned block interface, through WIN-001's documented API
against the virtual disk, mutates no pool or space metadata and is
an ordinary target. Everything that changes the space's own
geometry or membership — resize or delete the space, add or remove
members, retire a disk — is pool/space mutation: `Refused`.
Member-disk substrates refuse through the ordinary closure (their
pool-membership signature backs the pool). Two gates travel with
the permission: mutation inside a space is Regime C `blocked` when
the pool is degraded or a thin-provisioned space's allocation
headroom cannot be verified (the state layer's health facts), and
the write path is the platform's own supported API, never a raw
write to the virtual disk's backing. Cost of the broad alternative,
recorded: every Storage Spaces user loses NTFS resize for a
protection Section 2.1's own words ("pools/spaces") do not claim.

### 2.14 SI-30: sealed-volume deletion, severed and routed

**Recommendation: deletion-by-containing-erase is severable from
modification of the sealed object.**

- The sealed system volume and signed system snapshots, **as direct
  targets**, are `Refused` for every mutating class, in every
  environment, with no acknowledgment arm — Section 2.1's "never
  modified," absolute.
- A whole-container or whole-device destructive step that reaches
  the sealed volume **through the substrate closure** is governed
  not by the NonGoal arm but by a named, closed step family:
  boot-volume work on documented supported paths (Section 2.1's own
  second clause), which MAC-009 gates — `blocked` with the exact
  Recovery-only reason wherever macOS so gates it. **In v1 that
  family is empty**: no such step is implemented, every container
  erase reports `unsupported` as any unimplemented operation does,
  and the model carries the slot so that ADR-M1's eventual
  documented path becomes Regime C `blocked`-outside-Recovery
  without a protection-model change.

This keeps MAC-009 satisfiable in terms (round one's wall), keeps
the sealed object's own protection absolute, and answers the filed
axis: erasing the container is not a modification *of* the sealed
volume; it is boot-volume work, and boot-volume work has its own
normative route. The alternative — letting the sealed volume's
NonGoal arm refuse the container erase absolutely — is recorded as
rejected because it hard-codes `unsupported` for an operation
MAC-009's text contemplates as `blocked`, which is round one's
rejection re-shipped.

## 3. The adversarial round

**Attack 1 — "the acknowledgment arms are PART-014's bypassable
'without an explicit supported plan' returned."** Refuted on the
axis: the bypass the register condemned was a runtime gloss any
representable plan could talk past. Here the consumed-member arm has
no acknowledgment constructor — the bypass sentence is
unrepresentable — and the orphan arm's acknowledgment is typed,
hash-bound, names the parsed designator, and is re-derived at
validation: an acknowledgment whose object validation finds consumed
diverges and rejects. The escape exists exactly where refusing
forever would drive users to `zpool labelclear` outside the product,
which round three's review called the hazard the product exists to
prevent.

**Attack 2 — "the locked-layer acknowledgment destroys a hidden
pool; Section 2.1 is violated blind."** Sustained as a named
residual, not fixed: opacity is physical, and the helper cannot
enumerate through a locked container any more than the client can.
The design's honest scope is observable topology — ADR-0012 already
binds unrepresentability to the visible view — and the clause makes
the blind spot a typed, confirmed act (FS-010 plus the opacity
statement) rather than a silent default. Recorded as a limit with
its own sentence in the resolution banner, not rounded up.

**Attack 3 — "destruction-only reach misses mutation: move a pool
member and the pool is never reached, yet member bytes were
relocated."** The round's best attack; it amended the effect table
before this document was finished. Release-is-destruction was added
(a moved source extent, a shrink's tail, a deleted partition's range
are destroyed even when unwritten), relocation classes carry the
preserved-by-contract exemption for the moved subtree with the
byte-wise-signature-preservation obligation, and a consumed member
therefore refuses every mutating class that writes, releases, or
relocates its extent — not only overwrites. The worked
demonstration joins the regression set: shrinking a partition whose
released tail carries the L-F stale superblock is `blocked` pending
the release acknowledgment, which is the measured fixture family
engaging the closure.

**Attack 4 — "CAP-001 computes with no plan in scope; the
constructor computes with one; CAP-005 forbids them disagreeing, and
round three fell exactly here."** Sustained, and it produced clause
2.7's canonical-step rule: capability status for a mutating
operation is computed by running the same closure on the operation's
canonical effect-table entry for that target. One computation, two
callers; disagreement is not representable.

**Attack 5 — "the narrow SI-29 reading lets an NTFS grow force thin
allocation and fail mid-write inside a technology 2.1 protects."**
Partially sustained: the permission stands (allocation is the pool's
own runtime behavior through Windows' documented path, not an edit
of pool metadata), and the amendment is the Regime C health-and-
headroom gate in 2.13, which was not in the first draft of that
clause.

**Attack 6 — "2.14's routed exception is the absorption lemma
returning: a NonGoal node in the affected set that does not
refuse."** Sustained in form, tightened in consequence: the
exception is not an inspection escape but a **named, closed, empty-
in-v1 step family** with its own normative route (Section 2.1's
documented-paths clause plus MAC-009), and while it is empty the
sealed volume refuses through the closure like any other reached
NonGoal node. Nothing is absorbed silently; the slot exists so that
implementing Apple's own path someday is a Regime C matter, not a
closure amendment. The alternative absolute reading stays recorded
for Nate to prefer.

**Attack 7 — "the local-transport list's discriminants are
unmeasured: does Windows report NVMe-oF as BusType 17? If it does,
the list admits a fabric device as local."** Sustained as an
evidence obligation, not a design change: the fabric-versus-local
discrimination rows per platform join §5, and until a platform's row
exists, transports whose locality the state layer cannot positively
establish are `Indeterminate` — the list admits nothing by default,
because the arm requires a positive match *and* the discriminating
row. The cost is availability on unmeasured platforms, priced
deliberately.

**Attack 8 — "the closure in two languages is round three's costed
mirror; you waved it away."** Refuted by architecture rather than
waved: MODEL-005 requires byte-identical *hashing* cross-language,
which exists; verdict recomputation is an engine duty CAP-005
already centralizes, and the GUI reaches the engine in-process. The
decode-boundary closure re-run happens wherever the engine runs,
and no TypeScript surface is trusted for a verdict it displays
(CAP-007). What TypeScript owes — encoding parity and structural
validation — is what it already has. The rejected alternative and
its reason are recorded in 2.10.

**Attack 9 — "an unmounted generic-GUID `/boot` defeats the
PART-014 class function; 'exhaustive' is overclaimed."** Sustained
at bounded cost, stated in 2.8: Regime B attaches reasons and
confirmation strength and never flips status, so the miss costs a
warning on an offline volume, not a safety property; fstab-declared
purpose narrows the miss where readable. The class table is
exhaustive over the nine kinds; it is not omniscient over unmounted
generic partitions, and the ADR says so in terms.

**Attack 10 — "defer again: SI-27 is unresolved, and the closure
walks edges SI-27 has not named."** Rejected on the same ground
attack 4 of the SI-33 round fell: the closure depends on edge
*semantics* (containment, backing, production, host-backing), all
four of which exist in the surviving taxonomy or are named
obligations on SI-27's round, and the theorem's premise is stated
quantified so SI-27's additions either preserve it or re-prove it.
Sequencing the shape round after the naming round would leave the
naming round designing edges with no stated consumer — backwards.
Both resolve before increment 3 writes a type; this round hands
SI-27 its requirements list.

## 4. What this round does not do

- It does not resolve SI-37 (evidence clause unmet; home fixed,
  gate recommendation in 2.5), SI-28 (untouched; the floor and its
  ADR-0017 revisit route stand), or SI-27 (naming and edge typing;
  requirements handed over in 2.4 and 2.11).
- It does not demonstrate any refusal end to end: no write path
  exists. Every runtime demonstration lands as a named obligation
  (§5), beside the SI-33/SI-34/SI-35 banner obligations already
  binding the first write-capable increment.
- It does not relax anything: no arm in this design permits what the
  current state of the register forbids, and the acknowledgment arms
  gate populations that today simply cannot be typed at all.

## 6. If accepted, the mechanics

Governance reservation for ADR-0018 (subject-descriptive:
`0018-si11-protection-closure.md`); the ADR in the 0016 shape,
carrying the effect table, the arm enumeration, the PART-014 class

contents, and the closure commitment retexts Section 2.1's

deliberately not answered here; the register keeps it on the gate
